## 4. P0 问题

### P0-1：熔断恢复对账在交易所查询失败时可能 fail-open

影响范围：`/resume`、`/reconcile`、熔断恢复、新开仓恢复  
证据：

- `agents/trading/telegram_notifier.py:397-408` 初始化 OKX exchange 失败时直接 `pass`。
- `utils/position_reconciler.py:154-158` 在 `exchange is None` 时返回空持仓。
- `utils/position_reconciler.py:172-175` 交易所 `fetch_positions()` 异常时只记录日志并返回空持仓。
- `agents/trading/telegram_notifier.py:437-438` 只要 result status 是 `matched` 就允许恢复。

风险：

如果 OKX 凭证错误、网络失败、权限不足或 API 临时不可用，交易所真实持仓会被看作 `{}`。当本地 `data/positions.json` 也为空时，对账会返回 `matched`，Telegram `/resume` 可能解除熔断并恢复新开仓。这个路径必须 fail-closed。

修复建议：

1. `PositionReconciler._fetch_exchange_positions()` 返回 `(positions, error)` 或在 result 中加入 `exchange_query_ok=false`。
2. exchange 缺失、凭证缺失、`fetch_positions()` 异常时，`reconcile()` 必须返回 `status="error"` 或 `status="mismatch"`。
3. `/resume` 只允许 `status="matched"` 且 `exchange_query_ok=true` 时解除熔断。
4. 增加单测：`exchange=None`、`fetch_positions raises`、空本地持仓但交易所查询失败，均不得恢复。

## 5. P1 问题

### P1-1：`PositionAnalyst` 在新 BaseAgent 调度下存在同队列多消费者竞态

影响范围：持仓复核、批判官 verdict、execution_result 同步、减仓/平仓决策  
证据：

- `agents/base.py:55-59` 同时启动 `_message_loop()` 和 `_periodic_loop()`。
- `agents/trading/position_analyst.py:112-118` 的 `tick()` 仍手动 drain 自己的 bus queue。
- `agents/trading/position_analyst.py:173-177` 等待批判官 verdict 时再次直接 `bus.receive(self.name)`。

风险：

同一个 Agent 队列现在会被 `BaseAgent._message_loop()`、`PositionAnalyst.tick()`、`_evaluate_all_positions()` 内的等待循环同时消费。消息不会必然丢失，但 `on_message()` 可能并发修改 `_positions`、`_pending_reviews`、`_tech_cache`，导致：

- 已平仓持仓仍收到旧 verdict 后再次发出 close/reduce/add；
- execution_result 与 position_verdict 处理顺序不可控；
- 批判官超时逻辑和真实 verdict 处理互相竞争。

修复建议：

1. 移除 `PositionAnalyst.tick()` 中的手动 drain。
2. 批判官响应不要通过同队列同步 wait；改为 `on_message(position_verdict)` 更新状态，周期任务只检查 deadline。
3. 给 PositionAnalyst 增加单测：在评估期间插入 `execution_result.closed_externally` 与 `position_verdict`，不得再对已关闭仓位发布交易决策。

### P1-2：研判 barrier 缺少 cycle id，仍可能混用不同轮数据

影响范围：research 初选、新闻否决、情绪输入、SymbolRouter 候选池  
证据：

- `agents/orchestrator.py:129/142/152` 发布 `research_trigger` 时没有 cycle id。
- `agents/research/synthesizer.py:89-94` 只用 `_pending_data` 保存三类消息。
- `agents/research/synthesizer.py:109-143` 三类数据按消息类型覆盖，合成后清空。

风险：

本轮新增的 20s barrier 解决了“market 先到就立即初选”的问题，但如果上一轮 sentiment/news 在超时后才到达，它们会留在 `_pending_data`。下一轮 market 到达时，Synthesizer 可能把本轮 market 与上轮 sentiment/news 混在一起合成。

修复建议：

1. `research_trigger` 生成 `cycle_id` 和 `triggered_at`。
2. Market/Sentiment/News 输出必须带同一个 `cycle_id`。
3. Synthesizer 只聚合同 cycle 数据，超时后丢弃该 cycle 的迟到消息。

### P1-3：Judge 重启恢复只覆盖 `_open_positions`，关键交易状态仍会丢失

影响范围：并发持仓上限、同方向 SL 冷却、递增 cooldown、deferred entry、重复开仓保护  
证据：

- `agents/trading/judge.py:146-154` 从 `positions.json` 恢复 `_open_positions`。
- `agents/trading/judge.py:116-130` `_symbol_state` 中的 `last_force_close_time`、`deferred_entry`、`sl_timestamps` 等仍是内存态。
- `agents/trading/judge.py:153` 使用 `sym.replace('-SWAP', '')`，没有使用统一的 `utils.symbol.to_internal()`。

风险：

重启后并发持仓数量比第一次审计已有改善，但以下保护仍会失效：

- 刚触发 SL 的同方向冷却丢失；
- 连续 SL 的递增 cooldown 丢失；
- 等待回调/追价的 deferred entry 丢失；
- 如果 positions key 不是 `BASE-USDT-SWAP`，恢复格式可能不一致。

修复建议：

1. 用 `to_internal(sym)` 替代 `replace('-SWAP', '')`。
2. 将 `_symbol_state` 的关键字段原子持久化到 `data/judge_state.json`。
3. 启动时清理过期 deferred/cooldown，但保留仍有效的风险状态。

### P1-4：Ledger 生命周期接入不完整，限价开仓和加仓未记录真实 open/add 事件

影响范围：真实成交价、生命周期 PnL、外部平仓归因、账本审计  
证据：

- 市价 plan 开仓会调用 `ledger.record_open()`：`executor.py:723-733`。
- 限价开仓路径 `_execute_limit_order()` 返回 `(amount, fill_price)` 后，`open_position_with_plan()` 没有拿到 order id，也没有调用 `ledger.record_open()`：`executor.py:674-679`。
- 加仓路径 `add_to_position()` 创建订单后只用 ticker/current price 更新均价，没有 ledger 记录真实成交：`executor.py:1207-1268`。
- `LiveLedger.record_reduce()` / `record_close()` 依赖 `_find_open_position_id()` 找生命周期：`utils/live_ledger.py:56-63`。

风险：

限价单或加仓成交后，账本没有 open/add 事件，后续 reduce/close 可能写出 `position_id=None` 的事件，生命周期聚合缺失。`daily_realized_pnl()` 仍可能统计 close/reduce 事件，但生命周期级别的真实入场、手续费、归因、外部平仓审计不完整。

修复建议：

1. `_execute_limit_order()` 返回 order id、fill price、filled amount。
2. 限价成交和限价超时市价 fallback 都调用 `ledger.record_open()`。
3. `add_to_position()` 增加 `record_add()` 或复用独立 add event，并用真实成交价更新加权均价。
4. 增加单测覆盖：limit open -> reduce -> close 的 lifecycle 必须 closed 且有完整 events。

### P1-5：减仓 PnL 字段口径不一致，Reviewer 会漏记部分减仓收益

影响范围：Reviewer 交易历史、策略复盘、胜率/EV 输入、Telegram 展示  
证据：

- `ContractExecutor.reduce_position()` 返回 `realized_pnl`：`executor.py:1116-1117`。
- `ReviewerAgent` 对 `risk_reduced` 只读取 `result.get('pnl', 0)`：`agents/trading/reviewer.py:65-82`。
- PositionAnalyst 减仓路径会把 raw result 原样发布为 `risk_reduced`：`agents/trading/executor.py:208-211`。
- partial TP 路径也发布 raw result：`agents/trading/executor.py:543-552`。
- 只有 PortfolioRiskGuard 的组合风险减仓分支手动包装成 `{"pnl": realized_pnl}`：`agents/trading/executor.py:331-339`。

风险：

由 PositionAnalyst 或 partial TP 触发的减仓，真实 PnL 已进入 `RiskManager.record_trade()`，但 Reviewer 的 trade history 与策略复盘可能漏记，导致后续 rolling win rate、EV 估计和策略衰减判断偏差。

修复建议：

1. 统一执行结果字段：所有 close/reduce 同时包含 `pnl` 与 `realized_pnl`，或下游统一读取二者。
2. Reviewer `risk_reduced` 分支改为 `result.get('pnl', result.get('realized_pnl', 0))`。
3. Telegram 减仓通知也显示本次减仓 PnL。

### P1-6：早期持仓复核功能当前基本不会触发

影响范围：RQ-04 早期复核、入场后 30 分钟内风险控制  
证据：

- `MultiExecutor._early_review()` 依赖持仓字段 `open_time`：`agents/trading/executor.py:520-523`。
- `ContractExecutor._open_position()` 记录的 position 没有 `open_time`。
- `ContractExecutor.open_position_with_plan()` 记录的 position 也没有 `open_time`：`executor.py:740-760`。

风险：

新加的早期复核逻辑会把缺失 `open_time` 的仓位视为已持仓 999 分钟，从而跳过前 30 分钟复核。功能存在，但主开仓路径不会激活。

修复建议：

1. 所有 open/add/sync 补录路径写入 `open_time`。
2. 对从交易所同步回来的老仓位，写入 `open_time_synced_at` 并明确是否允许 early review。
3. 增加单测：新开仓 20 分钟且 -0.5R 时，SL 应被收紧。

### P1-7：CandidateRanker 只算分，没有执行 Top-N 选择

影响范围：多候选同时出现时的交易质量、到达顺序偏差  
证据：

- `utils/candidate_ranker.py:1-10` 文档说明会 buffer、ranking、只允许 Top-N 进入 live。
- `agents/trading/judge.py:854-862` 当前只直接调用 `_compute_rank_score()` 写入 attribution。
- 没有调用 `add_candidate()`、`rank_and_select()` 或 `flush_stale()`。

风险：

当前“候选排序”只是归因字段，不会阻止低排名候选先到先开仓。并发槽位紧张时，系统仍可能因为消息到达顺序选择较差交易。

修复建议：

1. 若短期只需要归因，重命名为 `CandidateScorer`，避免误解。
2. 若要实现 Top-N，Judge 应把开仓候选放入 buffer，在短窗口内统一排序后发布。
3. 加单测：两个候选同时到达、可用槽位 1，只能发布 rank_score 更高者。

### P1-8：LLM 降级告警加在旧 Judge，不在主交易 Judge

当前链路：

```text

  -> MultiDataCollector
  -> MultiTechAnalyst
  -> MultiJudge
  -> MultiExecutor + PaperExecutor
  -> execution_result
  -> RiskGuard / Reviewer / PositionAnalyst / Telegram
```

结论：

### 7.3 Halt / Resume Flow

当前链路：

```text

  -> HaltState.halt()
  -> system_command halt
  -> Executor / RiskGuard / PaperExecutor 停止新开仓

/resume
  -> HaltState.request_resume()
  -> PositionReconciler.reconcile()
  -> confirm_resume()
  -> system_command resume
```

结论：

- 全局 halt 状态和 paper mirror risk 是正确方向。
- 最大缺口是对账必须 fail-closed，不能在 exchange 查询失败时恢复。

### 7.4 Position Lifecycle / PnL Flow

当前链路：

```text
open/reduce/close order
  -> exchange fetch_order
  -> LiveLedger event
  -> lifecycle aggregation
  -> RiskManager daily_pnl sync
  -> Reviewer trade_history
```

结论：

- 市价开仓、普通平仓、减仓的基础账本能力已经建立。
- 限价开仓、加仓、外部平仓真实订单匹配还不完整。
- Reviewer 与 Executor 的 PnL 字段需要统一，否则策略复盘输入会偏。

## 9. 建议修复顺序

## 10. 总结

第二次审计确认：本轮代码更新确实解决了第一次审计里的多个关键工程问题，尤其是调度阻塞、配置文档口径、Telegram password、DataCollector 同步阻塞、RiskGuard 状态持久化、Paper/Live 隔离和实盘账本方向。

但当前最需要警惕的是“看起来有安全机制，异常时却没有 fail-closed”的路径：`/resume` 对账、Ledger 生命周期、PositionAnalyst 队列消费、Judge 状态恢复都属于这一类。建议先按 P0/P1 顺序收敛，再进入 OKX testnet 端到端矩阵验证。
