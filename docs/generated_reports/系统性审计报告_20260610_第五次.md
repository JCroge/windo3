## 2. P1 详述（对抗复核已坐实）

### P1-01　加仓破坏 TP invariant → 全局熔断（高频可触发的可用性事故）

**证据链（五段，逐行核对，调用链闭合）**：

1. `executor.py:3178-3183`（`add_to_position`）加仓后按新均价重算并写 `position['take_profit']`，整个函数体（3046-3213）**无任何** `take_profit_levels` 赋值，也不调 `_set_position_tp`；其调用的 `_replace_protective_sl`（3188）只管 SL。→ 加仓后 `take_profit != take_profit_levels[0]`。
2. 路径 live 可达：`position_analyst.py:366` 产出 `action='add'` →（`657-674`）映射成 `open_long/open_short` + `source='position_analyst'` → `agents/trading/executor.py:245-263` → `_execute_add_position` → `executor.add_to_position`。**触发门槛宽**（conviction≥70），是常规持仓管理动作，非边缘路径。
3. `_update_trailing` 顶部守卫（`executor.py:1923-1938`）：`tp_levels and tp_scalar is not None and tp_scalar != tp_levels[0]` —— **严格 `!=`，无浮点容差，不依赖 protection_state**。`check_stop_loss_take_profit`（1893）每轮调用 → 下一轮轮询必命中 → `_halt_symbol(reason='tp_invariant_breach')`（1931）。
4. `_halt_symbol`（`executor.py:925-937`）**无条件**调 `get_halt_state().halt()`，对 reason 不分流。
5. `halt_state.py:38-41` `can_open_new()=not halted and not reconciliation_pending` → False；`get_halt_state()` 是进程级单例，开仓门 `agents/trading/executor.py:157-165` 对**任意 symbol** 的开仓一律 reject。而 `clear_symbol_halt`（942-973）/ TG `/resume_symbol` 只清 in-memory `_halted_symbols`，**不清全局 halt** → 人工 `/force_resume` 或对账确认前**全系统冻结新开仓且不自愈**。

**影响**：单次合法加仓 → 全系统停止开新仓，availability 级生产事故。不直接造成错单或资损（halt 是 fail-closed 方向，已有持仓 SL/TP 仍在交易所侧），故 P1 而非 P0。**无任何测试覆盖"加仓后不 halt"**（现有 add 测试都在 TP 重算前就被 protection_state 拦截，1066 全绿掩盖了它）。

**对标**：Freqtrade `adjust_trade_position` 后经统一 `stoploss_on_exchange_update` 单点同步 SL/TP，不留 scalar 与 levels 双真相源。

**修复（单点，符合 CLAUDE.md 红线）**：`add_to_position` 重算 TP 后改为按 `tp_dist_pct` 同比例平移整个 `take_profit_levels`，并经 `_set_position_tp(position, new_tp, new_levels)` 单点收口写入——CLAUDE.md "Position TP 必须经 `_set_position_tp` 单一收口"红线，加仓路径正是漏网调用点。补"加仓后再跑 `_update_trailing` 不 halt"的同构测试。**置信度：高（0.9）**，残留不确定仅在实盘 add 触发频率。

> 关联 P2-02：`_halt_symbol` 把局部故障升级为全局停摆 + `/resume_symbol` 不能解除全局 halt，是本条影响面被放大的根因。建议同时处理：要么 `_halt_symbol` 区分 instrument-level 与 global-level，要么 `/resume_symbol` 文案明确提示"全局仍 halt，请用 /resume"。

### P1-02　短单 `or`-falsy：`range_pos=0.0` 旁路"别在底部追空" gate

**证据（实跑复现）**：`judge.py:2692` `range_pos = float(short_ctx.get('position_in_24h_range') or entry_ctx.get('position_in_24h_range') or 0.5)`。生产者 `tech_analyst.py:99` `(current_price - low_24h)/range_24h`，**无 clamp 到 [0.01,0.99]**，当价格触及 24h 最低时精确产出 `0.0`。`0.0` 是 Python falsy → 被 `or` 跳过取 `0.5` → gate `range_pos < 0.45`（`judge.py:2703`，阈值 `_short_live_min_range_pos=0.45`）失效。

独立 skeptic 实跑该函数（daily=bearish + range_pos=0.0 + pre_move=-0.005 浅跌 + rsi=45 + htf=3/3）：
```
range_pos=0.0   -> allowed=True   reason=''                       ← BUG（且归因写成 0.5，掩盖证据）
range_pos=0.001 -> allowed=False  reason='range_position_too_low' ← 正确
range_pos=0.3   -> allowed=False  reason='range_position_too_low' ← 正确
```
**主路径无任何函数外兜底**：`_apply_regime_policy`（正确写法 `.get(...,1.0)`）只在 deferred 三路径调用，主路径在 `judge.py:1529` 之前根本不调它；RSI<=30 硬门被 rsi=45 跳过；下游 executor/RiskGuard 无 range_pos 复核（grep 为空）。

**影响**：放行一笔"下跌趋势中砸到 24h 锅底"的反趋势短单，可直达执行、易吃反弹被打损——讽刺的是越靠近锅底（range_pos→0）反空风险越高，恰是这个最危险的点漏过。**触发需 `current_price` 严格等于 `low_24h`**（有微小浮点差则为极小正数、反被正确拦），故低频，P1 但不至 P0。

**修复**：`judge.py:2692-2694` 改 `or` 为显式 `None` 哨兵，与 `_apply_regime_policy:2915` 的 `.get(key, default)` 语义对齐；`pre_12h_return_pct`（2693）、`rsi`（2694，无后果）同类写法一并改。补 `range_pos=0.0` 短单回归用例。**置信度：高（0.97）**。

主干契约**总体健壮**（背压不丢 HIGH/CRITICAL、symbol-scoped 路由正确、执行结果 paper/live 独立 topic 隔离、holding flow 有 BC 超时兜底）。缺口：**P2-01**（censor→final 无超时 + watchdog 提前判完 → 标的池静默冻结至下一周期，建议 synthesizer 发 preliminary 后挂 final-stage 超时复用已有 `_salvage_from_preliminary`）+ **P2-06**（paper risk_alert 共享 topic，一行 `source` 守卫即根除）+ P2-13/14/15（add 路径 request_id/correlation 断链、close None 无 ack）+ **P2-16**（DLQ 无消费/告警，建议挂进已有 30s health loop）。

## 4. 对标辩驳结论（没有最优只有最适合）

对标 NautilusTrader / Freqtrade / Hummingbot / QuantConnect Lean 后，对这个**小资金 / 单人运维 / 单交易所 / LLM 辅助**系统的适配性判断：

### ✅ 保持（恰当，不要改）
1. **LLM 夹在 deterministic 规则之间 + 失败规则降级**——教科书级正确，命中 LLM-safety 共识（"用确定性基础设施包住非确定性"）。
2. **保护单 attach-algo 随开仓原子下发 + fail-closed posMode**——Freqtrade `stoploss_on_exchange` 同哲学。
3. **global halt + per-symbol halt 双层、全 deterministic**——比 Hummingbot 默认更细（但见 P2-02 的恢复语义需理顺）。
4. **asyncio 单事件循环自研总线（~200 行）**——避开多线程数据竞争，契合 NautilusTrader 单线程确定性哲学；**不要**换 Kafka/Ray/NATS。
5. **atomic write + 命名空间隔离的 JSON 状态**——**不要**上 DB/事件溯源 DB。
6. **"改策略必须同步事件回测"工程纪律**——parity 的低配正确版。
7. **不设人工下单批准**——单笔 30U cap 下自动化是对的，按 action-risk 定标正确。

### ⚠️ 补强（真实欠缺，均低成本）
1. **崩溃恢复路径统一**：当前是 `sync+reconcile` "重建"而非事件重放，恢复正确性取决于 reconciliation 覆盖度（对照 NautilusTrader crash-only "startup=recovery 同路径"）。叠加 P2-04 的伪造 SL，这是稳健性最该夯实的一块。
2. **背压/DLQ 不变量测试**：加断言"CRITICAL/HIGH topic 永不被背压丢弃 / 进 DLQ 即告警"（当前靠 `_PRIORITY_MAP` 不出错，脆弱）→ 对应 P2-16。
3. **LLM 层的 parity gap 文档化**：`event_backtest.py` 无法复现 LLM 非确定性修正，应像 Lean 诚实写清回测里 LLM 怎么处理（rule-fallback / record-replay）。
4. **下单 intent 先落 journal 再调 API**（Hummingbot "track before submit"）：验证"API 超时但订单已进场"是否只靠 10 分钟 reconciliation 兜底。

### 🔻 防过度（已有或潜在苗头）
1. `counterfactual_ledger` / `data_provenance` / dual-payload PnL 的精细度对单人单 venue 边际价值递减——**不是错，但若开始拖慢迭代，这是第一个该简化的地方**。
2. owner-tag clOrdId 的历史兼容分支（DEPRECATED + FR-3B 兼容）——单人系统可更激进：清历史挂单、删兼容路径。
3. **不要**因对标企业级就加：事件溯源 DB / Rust 重写 / 人工下单批准 / 外部消息中间件——对这个目标全是过度。

**一句话**：系统在"最容易出人命"的三处（LLM 护栏、保护单/熔断、parity 纪律）做对了关键决策；真实欠缺集中在"崩溃恢复的确定性"与"关键消息不丢的可证明性"，且都低成本可补；过度风险在 provenance/兼容分支的精细度，克制即可。
