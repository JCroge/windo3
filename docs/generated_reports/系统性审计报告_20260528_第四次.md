## 2. P0 Findings

### F4-001: `reduce_position()` 失败结果仍会被 Agent 当成成功 `risk_reduced` 广播

位置：

- `executor.py:2548-2565`
- `executor.py:2580-2617`
- `executor.py:2691-2711`
- `agents/trading/executor.py:225-233`
- `agents/trading/executor.py:442-454`
- `agents/trading/executor.py:1004-1020`
- `agents/trading/portfolio_risk_guard.py:144-147`
- `agents/trading/telegram_notifier.py:129-132`

问题：

`reduce_position()` 现在返回结构化 dict，并用 `ok/reduce_ok/replace_ok/protective_update_state` 表达结果。撤旧 SL 失败、reduce reject、residual SL 重挂失败时会返回 dict，其中 `ok=False` 或 `reduce_ok=False`。

但 Agent 层仍使用 `if result:` 判断成功：

- PositionAnalyst 的部分平仓路径只要 dict 非空就继续。
- `portfolio_exposure/correlation_risk` 风控减仓只要 dict 非空就发布 `status="risk_reduced"`。
- partial TP 路径只要 dict 非空就发布 `status="risk_reduced"`。

下游对 `risk_reduced` 的处理也没有检查 `result.ok/reduce_ok`：

- `PortfolioRiskGuard` 直接按 `payload.reduce_pct` 缩减本地 `amount_usdt`。
- `TelegramNotifier` 直接发“减仓 X%”。

影响：

- 撤旧 SL 失败时实际没有缩仓，但系统可能广播“已减仓”。
- reduce reject 时实际没有成交，但 RiskGuard 本地 exposure 会被缩小。
- partial TP 保护单失败时，Telegram 文案无法突出“减仓已成交但 residual protection failed”。
- 这会让风控视图低估真实敞口，并掩盖保护单故障。

修复要求：

1. Agent 层 reduce 结果必须按 `reduce_ok` 和 `ok` 分支处理：
   - `reduce_ok=false`：不得发布 `risk_reduced`；应发布 `status="rejected"` 或 `status="reduce_failed"`，reason 使用 `result.reason`。
   - `reduce_ok=true` 且 `ok=false`：可以发布已成交 reduce，但必须使用独立 `status` 或明确字段标识 `protection_failed`，并告警/halt。
   - `ok=true`：才是 clean `risk_reduced`。
2. `PortfolioRiskGuard` 不得仅按请求 `reduce_pct` 更新本地敞口；应优先使用 `result.actual_reduce_amount` 或新增 `actual_reduced_pct`。
3. `TelegramNotifier` 对 `protective_update_state=replace_failed/cancel_failed/restore_failed` 必须发故障文案。
4. 增加测试覆盖：
   - `_cancel_protective_sl=False` 时 Agent 不发布 `risk_reduced`。
   - `reduce_rejected` 时 RiskGuard 不缩减本地 exposure。
   - `replace_failed` 时广播含 `protection_state=unknown/halt_required`。

## 3. P1 Findings

### F4-002: `pnl_resolved` 总线事件没有完整透传 `final_close_cause/close_evidence`

位置：

- `utils/realized_pnl_resolver.py:70-150`
- `utils/realized_pnl_resolver.py:252-256`
- `agents/trading/executor.py:880-921`
- `utils/reconciliation.py:255-285`
- `agents/trading/executor.py:699-731`

问题：

Resolver 已经能输出：

- `close_cause`
- `final_close_cause`
- `is_strategy_stop`
- `close_evidence`

但 `_resolve_external_close_async()` 发布 `pnl_resolved` 时只透传了 `close_cause/is_strategy_stop`，没有透传 `final_close_cause` 和 `close_evidence`。

更严重的是定时 Reconciler 路径：

- `Reconciler.auto_resolve_pending()` summary 没有包含 `close_cause/final_close_cause/is_strategy_stop/close_evidence`。
- `MultiExecutor._run_reconciliation()` 发布 `pnl_resolved` 时也没有这些字段。

影响：

- 通过后台 Reconciler 升级的外部 SL，Judge 可能看不到 `is_strategy_stop=true`，不会补计 SL hit。
- 事件总线上缺少 close evidence，无法审计“为什么 final 被判定为 exchange_sl”。
- `test_external_close_final_cause.py` 只测 resolver 和 Judge 直接 payload，没有覆盖 Executor/Reconciler 发布事件，导致测试绿但总线契约不完整。

修复要求：

1. `Reconciler.auto_resolve_pending()` summary 透传：
   - `close_cause`
   - `final_close_cause`
   - `is_strategy_stop`
   - `close_evidence`
2. `_resolve_external_close_async()` 和 `_run_reconciliation()` 发布 `pnl_resolved/pnl_mismatch` 时透传同一字段集。
3. 新增 `resolution_id`，优先级建议：
   - `correction_event_id`
   - `supersedes_event_id`
   - `close_match_key`
   - `position_id + order_ids`
4. 增加端到端测试：mock Reconciler 返回 `exchange_sl` evidence，最终发布的 `pnl_resolved` 必须带 `close_evidence` 且 Judge 只计一次 SL hit。

### F4-003: 新 owner tag 生成器未用于实际 OKX SL 下单

位置：

- `executor.py:295-342`
- `executor.py:1464-1468`
- `executor.py:1949-1951`
- `executor.py:1068-1089`

问题：

代码新增了 `_make_owner_tag_clord_id()` 和 `_is_owner_clord_id()`，cleanup 也支持 `ca + namespace + bot_instance` owner prefix。但实际新 SL 下单仍在使用旧 `_make_sl_clord_id()`：

- `_replace_protective_sl()` 使用 `_make_sl_clord_id()`。
- `open_position_with_plan()` 的 attached SL 使用 `_make_sl_clord_id()`。
- legacy `_open_position()` 调 `_place_protective_sl()` 时没有传 clOrdId，`sl_algo_clord_id=None`。

这导致真实新挂的 OKX SL 并不会带新 owner prefix。当前 owner-bound cleanup 主要依赖本地 exact `sl_algo_id/sl_algo_clord_id`，测试中的 owner-prefix case 是合成数据，不证明真实新订单已 owner-tagged。

影响：

- 本地 state 丢失或跨进程重启后，系统不能通过 owner prefix 识别自己创建的 orphan SL。
- 多 bot 同账户运行时，新挂 SL 无法从 clOrdId 上证明归属。
- `docs/to-do-list.md` 中“owner-prefix 已落地”的表述高于代码事实。

修复要求：

1. OKX 新保护单统一使用 `_make_owner_tag_clord_id()`：
   - attach SL
   - `_replace_protective_sl()`
   - legacy `_open_position()` 独立 SL
2. live 环境要求显式配置 `BOT_INSTANCE_ID`；未配置时至少在启动 banner 和日志中告警。
3. 增加测试：
   - 新开仓 attached SL 的 `attachAlgoClOrdId` 以当前 owner prefix 开头。
   - replace SL 的 `algoClOrdId` 以当前 owner prefix 开头。
   - legacy open 独立 SL 也写入 `sl_algo_clord_id`。

## 4. 已确认闭环项

- 新闻 ticker mention 已收敛到 `utils/symbol_mentions.py`，短 ticker substring 误报有专门测试覆盖。
- default / network 测试体系本轮均可收敛执行。
