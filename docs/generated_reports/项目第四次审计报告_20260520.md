## 6. P1 问题

### P1-1：LLM degraded 告警仍未真正打通 Telegram，且连续失败计数不准确

影响范围：LLM API 异常、系统降级可观测性、无人值守运行。

证据：

- `MultiJudge._ask_llm()` 失败 3 次后 publish `risk_alert`，payload 使用 `"alert_type": "llm_degraded"`：`agents/trading/judge.py:1990-2005`。
- `TelegramNotifier._handle_risk_alert()` 读取的是 `payload.get('type')`，不是 `alert_type`：`agents/trading/telegram_notifier.py:144-147`。
- Telegram 只推送 `flash_move`、`max_drawdown`、`emergency_close` 三类 critical 风控告警：`agents/trading/telegram_notifier.py:150-152`。
- `_llm_consecutive_failures` 只在异常时递增，成功返回时没有重置：`agents/trading/judge.py:1982-1989`、`agents/trading/judge.py:1993-2005`。

风险：

主交易 Judge 进入规则降级时，运维侧可能完全无感。更严重的是，失败计数不是严格“连续失败”：两次失败后即使中间成功一次，下一次失败仍可能触发“连续3次失败”告警。

建议：

1. 成功调用 LLM 后重置 `_llm_consecutive_failures = 0`，并在恢复时允许再次告警。
2. 直接 publish `telegram_alert`，或统一 `risk_alert` schema 为 `{"type": "llm_degraded"}`。
3. Telegram critical 类型加入 `llm_degraded`，并增加测试覆盖。
4. 优先复用 `LLMClient.consecutive_failures/degraded`，避免 Judge 自己维护另一套计数。

### P1-2：加仓账本仍会创建新的 open lifecycle，导致生命周期审计不闭环

影响范围：实盘加仓、真实 PnL lifecycle、外部平仓归因、账本审计。

证据：

- `add_to_position()` 下单成功后调用的是 `self.ledger.record_open(...)`：`executor.py:1235-1244`。
- `LiveLedger.record_open()` 每次都会生成新的 `position_id` 并 `_open_lifecycle()`：`utils/live_ledger.py:29-54`。
- `LiveLedger._find_open_position_id()` 对同一 symbol/side 只返回第一个 open lifecycle：`utils/live_ledger.py:338-343`。

风险：

一笔真实持仓经过加仓后，账本会出现两个 open lifecycle。后续 reduce/close 通常只会匹配第一个 open lifecycle，第二个加仓 lifecycle 可能长期保持 open，形成幽灵生命周期，复盘、审计和外部平仓匹配都会失真。

建议：

1. `LiveLedger` 增加 `record_add()`，查找当前 open lifecycle 并追加 `event_type="add"`。
2. lifecycle 内维护 `total_amount_usdt`、`avg_entry_price`、`events=["open","add",...]`。
3. `executor.add_to_position()` 调用 `record_add()`，不要调用 `record_open()`。
4. 增加 `open -> add -> reduce -> close` 的 lifecycle 测试，断言最终只有一个 closed lifecycle。

### P1-3：CandidateRanker 仍未参与实际 Top-N 裁决

影响范围：并发持仓槽位、机会选择质量、强弱信号排序。

证据：

- `utils/candidate_ranker.py` 文件头明确写明 `rank_and_select() 已实现但未被 Judge 调用`：`utils/candidate_ranker.py:1-5`。
- Judge 当前只调用 `_compute_rank_score()` 写入 attribution：`agents/trading/judge.py:1062-1070`。
- 并发上限仍在单个 `tech_analysis` 到达时即时判断：`agents/trading/judge.py:376-392`。

风险：

当多个标的在同一窗口内同时出现开仓条件，系统仍是“先收到先占槽”。弱信号先到可能占用并发名额，强信号稍后到达时被拒绝。这会削弱新增 ranking 的实际交易价值。

建议：

1. Judge 引入短窗口 candidate buffer，例如 3-10 秒。
2. 到窗口结束或槽位即将满时调用 `rank_and_select(open_positions)`。
3. selected 发布实盘 `trade_decision`，rejected 发布 hold 或 paper-only 观察事件。
4. 增加测试：3 个槽位已占 2 个、同窗口 3 个候选，只有 rank_score 最高者进入 live。

### P1-4：Research 第二阶段仍缺 `cycle_id`，迟到审查可能串轮

影响范围：研究层选币、SymbolRouter 标的更新、长时间运行后的候选新鲜度。

证据：

- Synthesizer 已在第一阶段根据 `research_market_data.cycle_id` 切换 cycle：`agents/research/synthesizer.py:113-123`。
- `research_preliminary` 已带 `cycle_id`：`agents/research/synthesizer.py:194-199`。
- `Censor` 发布 `research_challenge` 时没有继续带 `cycle_id`：`agents/research/censor.py:87-92`。
- `Synthesizer._final_decision()` 收到 `research_challenge` 后不校验 cycle，直接消费当前 `_preliminary_result`：`agents/research/synthesizer.py:201-262`。

风险：

如果 cycle A 的 Censor 调用较慢，cycle B 已经生成新的 `_preliminary_result`，迟到的 A 审查可能与 B 的初选结果混合，产生错误的 `research_result`。这类问题在本地短测试中不容易出现，但长时间运行和 LLM API 波动时风险较高。

建议：

1. `Censor` 在 `research_challenge` 中透传 `cycle_id`。
2. `Synthesizer._final_decision()` 校验 challenge cycle 与当前 preliminary cycle，不一致直接丢弃。
3. `_preliminary_result` 内保存 `cycle_id`，不要只依赖 `_current_cycle_id`。
4. 增加测试：A preliminary 后 B preliminary，A challenge 迟到时不得产生 B 结果。

### P1-5：deferred pullback / chase 开仓仍缺 attribution

影响范围：15m 优化复盘、原型 cooldown、Reviewer 统计、真实开仓可解释性。

证据：

- `deferred_15m_confirmation` 已构建 attribution：`agents/trading/judge.py:473-490`。
- `deferred_pullback` 发布 open decision 时没有调用 `_build_attribution()`，plan 也没有 `plan['attribution']`：`agents/trading/judge.py:527-565`。
- `deferred_chase` 发布 open decision 时也没有 attribution：`agents/trading/judge.py:601-642`。
- Executor 只有在 decision 带 attribution 时才会传递到 result/position：`agents/trading/executor.py:198-204`。

风险：

这两类开仓即使已经走了 15m 二次确认和 quality gate，后续也无法完整回答“这笔单是否 15m 确认、HTF 几票、LLM 是否同向、rank_score 多高”。原型 cooldown 也可能因缺 attribution 无法记录失败原型。

建议：

1. 将 open decision 构建统一成 helper，所有 live open 路径必须生成 attribution。
2. pullback/chase attribution 至少包含 `entry_type`、`signal_score`、`htf_votes`、`tf_15m_*`、`rr_bucket`、`ev_at_entry`。
3. 增加测试：deferred_pullback 和 deferred_chase 的 execution_result 中必须含 attribution。
