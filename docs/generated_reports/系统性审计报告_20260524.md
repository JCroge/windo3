## 2. 对标框架校验

本项目是单进程、小账户、低并发、研究驱动型交易系统，不适合直接搬重型机构框架。但成熟项目能验证哪些边界不能省。

| 对标对象 | 官方依据 | 对本项目的校验结论 |
|---|---|---|
| CCXT sandbox/testnet | https://github.com/ccxt/ccxt/wiki/manual#testnets-and-sandbox-environments | sandbox 必须在 exchange 创建后、任何调用前启用。本项目新增 `utils/exchange_factory.py` 后，Research scanner、DataCollector、Judge、Telegram reconciliation 已统一；根 `executor.py` 仍直接创建 ccxt，但也在构造阶段调用 `set_sandbox_mode(True)`。 |

## 3. 系统层审计

### 3.1 启动与环境边界

当前生产主入口为 `run_agents.py`，`start.sh` 已启动 `python3 run_agents.py`。`main.py` 运行即提示 deprecated 并退出，`live_trading.py` 只作为旧单策略调试参考，不应作为生产入口。

配置加载由 `utils/config_loader.py` 处理，环境变量覆盖配置文件，live 缺凭证会拒绝启动。`USE_TESTNET=true` 时主要 exchange 创建路径通过统一 factory 设置 sandbox。当前适合 paper/testnet/小额 live 灰度，但扩容前必须补 OKX 真实 testnet 记录。

### 3.2 状态与恢复

`utils/halt_state.py` 已对坏状态文件 fail-closed：加载损坏 `halt_state.json` 后进入 halted + reconciliation pending。Telegram `/resume` 不再直接最终修改 HaltState，而是执行对账后向 Executor 发 `system_command resume`；Executor 是恢复状态 owner。

`utils/position_reconciler.py` 已区分 `blocking_issues` 和 `advisory_issues`，paper/live mismatch 默认不阻塞恢复，符合 paper 影子账户隔离目标。

### 3.3 事件可靠性

`agents/message_bus.py` 已有优先级、背压、DLQ、无人订阅重要 topic 记录；`utils/event_journal.py` 记录 `trade_decision`、`execution_result`、`daily_hard_stop_triggered`、`risk_alert`、`system_command` 等关键事件。以当前单进程规模看，先用 JSONL journal 是合适的，不需要立刻引入 Kafka、Redis Stream 或工作流引擎。

剩余风险是 journal 还不是完整 replay 引擎，进程崩溃时仍可能丢失已入队未消费的低优先级消息。关键交易事件已经比上一轮明显改善。

## 4. 架构层审计

整体架构为 Research 层慢频选标的、Trading 层快频分析和执行：

```text
Research: research_trigger -> Market/Sentiment/News -> Synthesizer -> Censor -> SymbolRouter -> symbol_update
Trading: symbol_update -> DataCollector -> TechAnalyst -> Judge -> Executor/PaperExecutor -> Reviewer/RiskGuard/PA/Telegram
Holding: PositionAnalyst -> BehavioralCritic -> PositionAnalyst arbitration -> trade_decision close/reduce/add
Risk: Reviewer/RiskGuard -> daily_hard_stop_triggered/risk_alert -> Executor
```

该结构符合当前目标。继续抽象 PortfolioConstruction 或外部工作流引擎不是短期最重要事项。下一阶段最重要的是把 OKX 真实语义、LLM 字段契约、paper/live 复盘隔离和观测链路压实。

## 5. Agent 与 LLM 审计

| 模块 | 当前状态 | 审计判断 |
|---|---|---|
| `LLMClient` | JSON 解析、schema 校验、prompt injection warning、审计日志、7 天清理 | 可用；但审计日志记录 `user_msg`/`raw_response`，建议增加脱敏和可配置保留天数。 |
| ResearchSynthesizer | 已传 `SYNTHESIS_SCHEMA` / `FINAL_SYNTHESIS_SCHEMA` | 上一轮 schema 缺口已关闭。 |
| Censor | 已传 `CENSOR_SCHEMA` | 可用。 |
| TechAnalyst | 已传 `TECH_ANALYST_SCHEMA` | 可用。 |
| Judge | 已传 `JUDGE_DECISION_SCHEMA`，并有 rule/EV/risk gate | 是主决策 owner，open 主链路契约最完整。 |
| BehavioralCritic | 已传 `BEHAVIORAL_CRITIC_SCHEMA` | 存在字段命名不一致风险，见 F-002。 |

关键发现：`BEHAVIORAL_CRITIC_SCHEMA` 定义 `counter_action` 和 `confidence`，但 prompt 与规则降级输出 `counter_recommendation`、`confidence_in_challenge`，而 `PositionAnalyst` 读取 `counter_recommendation`。如果 LLM 严格按 schema 输出，PA 可能拿不到批判官反向建议；如果 LLM 按 prompt 输出，schema 又会补默认字段并保留额外字段。当前因为 validator 透传额外字段，链路不一定立刻断，但这是契约不严谨。

## 7. Flow-by-flow 审计

### Flow 1：启动

`run_agents.py -> Orchestrator -> MessageBus.reset -> register agents -> agent.run()`。结论：可用。setup 阶段失败仍缺少自动 supervisor restart，属于 P2 运维成熟度。

### Flow 2：Research 选币

三路研究数据到齐或超时后 Synthesizer 初选，Censor 逆向审查，再终选并发 `symbol_update`。结论：适合当前慢频选币目标。轻微风险是 `_preliminary_result` 仍是单 slot，极端重叠 cycle 可能覆盖。

### Flow 3：标的路由

SymbolRouter 维护 active symbols，removed symbol 可触发 close。结论：策略上可接受，但应在 Reviewer 里持续观察换手和 removed close 的真实收益影响。

### Flow 4：行情采集

DataCollector 分 10s/30s/60s/300s/30min 多频率采集。contractSize 对 orderbook/liquidation 已修复；big trade 仍更像 ratio/压力信号，命名上不应被下游误读为 OKX 可执行 USD 深度。

### Flow 5：技术分析

TechAnalyst 输出观察，不直接下单。闭合 K 线、15m 入场确认、4h/1d 多周期信息完整。结论：职责边界正确。

### Flow 6：Judge 决策

Judge 汇总 rule score、LLM、R:R、EV、ranking、slot gate，open 决策通过 `_gate_and_publish_open()` 生成 `request_id` 和 `trade_decision.v2`。short-side bucketed EV 已修复并有测试。结论：open 主链路可以继续 paper/live 小额观察。

### Flow 7：实盘执行

MultiExecutor 执行 halt、余额、风控、持仓冲突、预检、下单和统一 `execution_result.v2` 发布。底层 `ContractExecutor` 仍是 OKX 语义风险集中点，尤其 `attachAlgoOrds`、reduceOnly、move SL、close 后条件单状态，必须做真实 testnet。

### Flow 8：Paper 执行

PaperExecutor 订阅同一 `trade_decision`，独立状态，发布 `paper_execution_result`。结论：隔离合理。后续若要用 paper 反哺 EV，应做单独 paper reviewer，不要污染 live Reviewer。

### Flow 9：风控与恢复

Reviewer Daily Hard Stop、RiskGuard alert、Telegram halt/resume、HaltState 持久化已经形成闭环。恢复前对账会读取 executor/riskguard/paper/exchange。结论：自动化层面已从 fail-open 风险收敛到 fail-closed，但真实 exchange 查询语义还要 testnet 验证。

### Flow 10：持仓管理

PositionAnalyst 7 因子评分后调用 BehavioralCritic，最终发 close/reduce/add。结论：方向正确；需要统一 critic counter 字段，并考虑给 PA 输出也补 `request_id/schema_version`。

### Flow 11：复盘与 EV

Reviewer 记录 live `execution_result` 并给 Judge segmented metrics。结论：正期望闭环雏形成立。Paper 结果不进入同一 Reviewer 是合理隔离，但需要独立报表，否则 paper/live 对照不够清晰。

### Flow 12：运维与观测

日志、LLM audit、event journal、Telegram command、MessageBus metrics 都已存在。结论：可用但未形成统一 health page；P2 继续补 Agent setup health、DLQ、LLM degraded、data degraded、queue backlog。
