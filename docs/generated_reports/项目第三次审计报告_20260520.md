## 6. P1 问题

### P1-1：15m 数据只校验长度，不校验新鲜度；`required=true` 下仍可能 fail-open

影响范围：15m 入场确认、实盘开仓方向、行情源异常时的保守性  
证据：

- `_collect_15m()` 成功时只写 `health['klines_15m']`，没有写入采集时间：`agents/trading/multi_data_collector.py:638-644`。
- `_collect_15m()` 失败时只打 warning，没有清空旧缓存，也没有标记 15m stale：`agents/trading/multi_data_collector.py:645-646`。
- `_full_collect()` 直接从 health 读取旧 `klines_15m` 并发布：`agents/trading/multi_data_collector.py:330-349`。
- `data_quality.tf_15m_ok` 只判断 `len(klines_15m) >= 50`：`agents/trading/multi_data_collector.py:361-369`。
- `TechAnalyst` 只要 `len(klines_15m) >= 30` 就认为可用：`agents/trading/tech_analyst.py:242-265`。

风险：

如果 15m 拉取失败、网络抖动或交易所返回延迟数据，系统会继续使用上一次缓存的 15m K 线。`entry_timing_15m_required=true` 的语义应是“缺失或过期即禁止新开仓”，但当前只要旧缓存长度足够，Judge 就会把它当作可用 15m。这个缺口会直接削弱本轮为解决 15m 背驰所做的优化。

建议：

1. `health['klines_15m_updated_at']`、`health['klines_15m_last_ts']` 必须进入 payload。
2. 15m 最新已闭合 K 线距离当前时间超过 2 个 15m 周期时，`tf_15m_available=false`。
3. `_collect_15m()` 失败时写入 `tf_15m_error`，并让 Judge 在 required=true 时 fail-closed。
4. `TechAnalyst` 的可用阈值与 `data_quality.tf_15m_ok` 统一，建议都用 `>=50`。

### P1-2：`deferred_15m_confirmation` 开仓路径绕过部分质量门，且没有 15m attribution

影响范围：15m deferred 入场、原型 cooldown、Reviewer 归因、复盘统计  
证据：

- `deferred_15m_confirmation` 触发后只执行 `_reconfirm_deferred()`、R:R、EV，没有调用 `_open_quality_rejection()`：`agents/trading/judge.py:371-396`。
- 该路径直接构造 `trade_decision`，没有调用 `_build_attribution()`：`agents/trading/judge.py:400-408`。
- `deferred_pullback` 和 `deferred_chase` 也发布 open decision，但没有 attribution：`agents/trading/judge.py:472-480`、`agents/trading/judge.py:549-557`。
- 正常 live open 才会构建 attribution 并写入 plan：`agents/trading/judge.py:974-999`。

风险：

15m 反向后等待转向再开仓是这次优化的核心路径。如果这条路径少了 open quality gate，原型 cooldown、部分流动性/质量归因和后续 Reviewer 统计会不完整。更重要的是，需求要求“每笔开仓能看到 15m 是否确认”，当前 deferred open 不满足。

建议：

1. 所有 deferred open 在发布前统一调用 `_open_quality_rejection()`。
2. 所有 open decision 都通过一个统一 builder 生成 `entry_type`、`attribution`、`plan['attribution']`。
3. `deferred_15m_confirmation` 的 attribution 必须包含 `tf_15m_entry_status=confirmed|neutral`、等待时长、原始 block reason。

### P1-3：Research `cycle_id` 修复不完整，下一轮研判可能被丢弃

影响范围：研究层选币、SymbolRouter 标的更新、长时间运行后的候选新鲜度  
证据：

- Orchestrator 已为每轮 research 生成新 `cycle_id`：`agents/orchestrator.py:128-154`。
- Synthesizer 在发现 `incoming_cycle != self._current_cycle_id` 时直接丢弃消息：`agents/research/synthesizer.py:113-116`。
- 只有 market data 到达时才会设置 `_current_cycle_id`，但这段逻辑在 mismatch 判断之后：`agents/research/synthesizer.py:118-120`。
- `_preliminary_synthesis()` 清空 `_pending_data`，但没有重置 `_current_cycle_id`：`agents/research/synthesizer.py:151-156`。
- `research_preliminary`、`research_challenge`、`research_result` 均未继续携带 cycle id：`agents/research/synthesizer.py:191-195`、`agents/research/censor.py:87-92`、`agents/research/synthesizer.py:251-257`。

风险：

第一轮 market data 会把 `_current_cycle_id` 锁定为 A。第二轮 market data 带 cycle B 到达时，因为 B != A，会在更新当前 cycle 前被丢弃。结果是系统可能只完成首轮研判，后续定时/空闲研判不再有效。即使绕过该问题，第二阶段 Censor/SymbolRouter 没有 cycle id，也仍可能吃到迟到审查结果。

建议：

1. 收到 `research_trigger` 时由 Synthesizer 显式开启新 cycle，或允许 `research_market_data` 切换到新 cycle 并清空旧 pending。
2. `_preliminary_synthesis()` 完成后记录 cycle 状态，不要让旧 `_current_cycle_id` 阻止新 cycle。
3. `research_preliminary -> research_challenge -> research_result -> symbol_update` 全链路传递 cycle id。
4. 增加测试：连续两轮不同 `cycle_id`，第二轮必须能产生 `research_preliminary`。

### P1-4：Ledger 限价开仓和加仓生命周期仍不完整

影响范围：真实成交价、生命周期 PnL、外部平仓归因、账本审计  
证据：

- 市价 plan open 会调用 `ledger.record_open()`：`executor.py:719-735`。
- 限价 open `_execute_limit_order()` 返回 `(amount, fill_price)`，没有返回 order id：`executor.py:790-896`。
- `open_position_with_plan()` 对限价返回结果后没有 `ledger.record_open()`：`executor.py:676-680`、`executor.py:742-765`。
- `add_to_position()` 创建市场单后用 ticker/current price 更新均价，没有 ledger open/add event：`executor.py:1210-1221`。

风险：

一旦真实运行中大量使用限价单或 PositionAnalyst 加仓，账本会缺少开仓/加仓事件，后续 reduce/close 可能只能记录零散 PnL，生命周期归因不完整。Daily PnL 可能仍能通过 close/reduce 事件近似统计，但审计链条不完整。

建议：

1. `_execute_limit_order()` 返回 order id、filled amount、fill price。
2. 限价成交和限价超时 fallback 都调用 `ledger.record_open()`。
3. LiveLedger 增加 `record_add()`，并维护加权均价和生命周期 events。
4. 增加 `limit open -> reduce -> close` 与 `open -> add -> close` 的 lifecycle 断言。

### P1-5：CandidateRanker 仍只算分，没有实际 Top-N 选择

影响范围：多候选同时出现时的交易质量、并发槽位稀缺时的选择公平性  
证据：

- `CandidateRanker` 文档声明会 buffer、排序、只让 Top-N 进入 live：`utils/candidate_ranker.py:1-10`。
- `rank_and_select()` 已实现但未被 Judge 调用：`utils/candidate_ranker.py:43-88`。
- Judge 只调用 `_compute_rank_score()` 写 attribution：`agents/trading/judge.py:979-987`。
- 代码搜索没有 `add_candidate()` / `rank_and_select()` 调用。

风险：

当前系统仍是“谁先到、谁先占槽”。当多个标的同时满足开仓条件时，rank_score 不会阻止低质量候选先开仓，高质量候选可能因为并发持仓上限被挡掉。

建议：

1. 短期如果只做归因，应把 `CandidateRanker` 改名为 `CandidateScorer`，避免误判功能已上线。
2. 如果要上线 Top-N，Judge 应在短窗口内 buffer 候选，统一排序后发布 open，其余进入 paper 观察。
3. 增加测试：可用槽位 1、两个候选同时出现，只允许 rank_score 更高者 live open。

### P1-6：Judge 关键风险状态仍未持久化

影响范围：重启后的 SL cooldown、deferred entry、重复开仓保护、原型冷却  
证据：

- Judge setup 只从 `positions.json` 恢复 `_open_positions`：`agents/trading/judge.py:154-170`。
- `_symbol_state` 中 `last_force_close_time`、`last_open_time`、`deferred_entry`、`sl_timestamps` 仍只在内存中：`agents/trading/judge.py:123-137`。

2. 启动时清理过期 deferred/cooldown，但保留仍有效的风险状态。

同一标的同方向在同一秒内重复开 lifecycle 理论上会覆盖。幂等窗口降低概率，但账本层应使用不可碰撞 id。

### P2-7：真实 OKX testnet 矩阵仍缺失

本轮 pytest 全过，但仍没有真实验证：

- market open with `attachAlgoOrds`
- limit open with attached TP/SL
- limit timeout fallback to market
- reduceOnly partial close
- add 后旧 SL 取消与新 SL 重挂
- 外部 TP/SL 触发后的 sync、ledger external close、Reviewer 记录
- `/halt`、`/resume`、`/force_resume` 端到端

## 8. Flow 审计结论

### 8.1 Research Flow

当前链路：

```text
research_trigger(cycle_id)
  -> MarketScanner / SentimentResearcher / NewsResearcher
  -> ResearchSynthesizer barrier
  -> research_preliminary
  -> Censor
  -> research_result
  -> SymbolRouter
  -> symbol_update
```

结论：

- 三路数据带 cycle id 是正确方向。
- 但 Synthesizer 当前 cycle 切换逻辑有 P1 缺陷，可能导致第二轮及以后 market data 被丢弃。
- 第二阶段尚未传递 cycle id，迟到 `research_challenge` 仍可能污染当前结果。

### 8.2 Trading / 15m Flow

当前链路：

```text
market_data(1h + 15m + 4h + 1d)
  -> TechAnalyst.entry_timing
  -> Judge score / EV / R:R / RSI / quality gate
  -> 15m entry timing filter
  -> trade_decision open 或 deferred_15m_confirmation
```

结论：

- 正常 open 路径已经能阻止 15m 明确反向。
- 15m 使用已闭合 K 线，这是正确实现。
- 关键缺口是 15m 数据新鲜度和 deferred open 的统一归因/质量门。

### 8.3 Halt / Resume Flow

当前链路：

```text
/halt 或 daily_hard_stop
  -> HaltState.halt()
  -> Executor / RiskGuard / PaperExecutor 禁止新开仓

/resume
  -> HaltState.request_resume()
  -> PositionReconciler.reconcile()
  -> matched && exchange_query_ok
  -> HaltState.confirm_resume()
```

结论：

- 二审 P0 已关闭。
- 当前恢复链路比之前更安全。
- `/status` 展示仍需跟上 HaltState。

### 8.4 Execution / Ledger Flow

当前链路：

```text
Judge plan
  -> MultiExecutor
  -> ContractExecutor open/reduce/close
  -> LiveLedger event
  -> RiskManager / Reviewer / Telegram
```

结论：

- 市价 open、普通 close、reduce 的账本能力可用。
- limit open 和 add 仍是生命周期缺口。
- Reviewer 的 reduce PnL 口径已修复。

### 8.5 LLM Flow

结论：

- LLM schema、输入清理、规则降级都在。
- 主交易链路的 degraded 告警仍未闭环。
- LLM 不应也不能绕过 15m、EV、R:R、余额、熔断和执行器预检；当前正常路径满足这个原则。

## 9. 建议修复顺序

### 9.1 先修 15m 闭环

1. 给 `klines_15m` 增加采集时间、最新已闭合 K 线时间和 stale 判断。
2. `entry_timing_15m_required=true` 时，15m 缺失或 stale 必须禁止新开仓。
3. 所有 deferred open 统一走 open quality gate、attribution builder 和 plan attribution。
4. 15m neutral 强信号放行增加 HTF 同向条件。
5. 增加 15m 端到端测试。

### 9.2 再修研究层

1. 修正 Synthesizer cycle 切换逻辑，确保第二轮、第三轮 research 不被丢弃。
2. `research_preliminary`、`research_challenge`、`research_result`、`symbol_update` 全链路带 `cycle_id`。
3. 增加连续两轮 cycle 的测试。

### 9.3 实盘恢复前必须完成

1. Ledger 补齐 limit open 和 add 生命周期。
2. Judge state / archetype cooldown 持久化。
3. CandidateRanker 要么真正 Top-N，要么改名为 scorer。
4. 主交易 Judge 或 BaseAgent 增加 LLM degraded Telegram 告警。
5. Telegram `/status` 展示 HaltState、对账结果、LLM degraded。

### 9.4 OKX testnet 矩阵

完成以上 P1 后，再跑 OKX testnet 矩阵：

```text
market open + attached TP/SL
limit open + attached TP/SL
limit timeout fallback
reduceOnly partial close
add + SL update
external TP/SL -> sync -> ledger external_close
/halt -> /resume -> reconciliation
```

## 10. 总结

第三次审计确认：代码更新确实把 15m 入场确认层做进了主交易链路，正常路径已经能阻止“开多时 15m 明显空头 / 开空时 15m 明显多头”的开仓。

但当前还不能把“15m 背驰问题”判定为完全关闭。真正需要补的是异常和 deferred 场景：

- 行情源异常时，15m 不能用旧缓存冒充可用数据。
- 等待 15m 转向后再开仓的路径，必须和正常 open 一样经过质量门、归因和复盘字段。
- 研究层 cycle id 需要修正，否则长时间运行后选币轮换可能失效。

建议先按 9.1 和 9.2 收敛，再进入 OKX testnet 端到端验证。
