## 4. 阻塞项

### P0-1 Deferred open flow 绕过 final slot gate / Ranking / pending reservation

位置：

- `agents/trading/judge.py:507-539`
- `agents/trading/judge.py:610-649`
- `agents/trading/judge.py:708-736`
- `agents/trading/judge.py:793-829`

当前 `_make_decision()` 开头的并发保护只在“所有 slot 都满”时才提前 hold：

```python
if main_count >= max and low_rr_count >= low_rr_cap and probe_count >= probe_cap:
    hold
```

这对“还不知道 plan 会落到哪个 slot”的早期门来说可以理解，但 deferred flow 后面在 plan 确定后没有复用主路径 final gate：

- `deferred_15m_confirmation` 构建 plan 后直接 `publish("trade_decision")`。
- `deferred_pullback` 构建 plan 后直接 `publish("trade_decision")`。
- `deferred_chase` 构建 plan 后直接 `publish("trade_decision")`。

这些路径没有：

- 调用 main / low_rr / probe final slot gate。
- 进入 `CandidateRanker.add_candidate()`。
- 添加 `_pending_open_symbols`。
- 添加 `_pending_open_slots`。
- 添加 `_pending_open_ts`。

可达风险场景：

1. main slot 已满，但 low_rr 或 probe slot 还有空，早期门不会阻止。
2. deferred flow 最终生成普通 main plan。
3. 因为没有 final main slot gate，仍然直接 publish live open。

另一个可达场景：

1. low_rr_extra 已满，但 probe slot 空。
2. 早期门仍放行。
3. deferred flow route 成 `low_rr_extra` 后直接 publish，绕过 low_rr cap。

probe 场景同理：

1. 两个 deferred short 几乎同时满足 `degrade_to_probe`。
2. 在 execution_result 回来前没有 pending reservation。
3. 两个 probe 都可能 direct publish。

验收影响：

- AC-SHORT-03 “同时最多 1 个 probe_short”不能算全 flow 通过。
- AC-RR 低 R:R slot 分层不能算全 flow 通过。
- `MAX_CONCURRENT_POSITIONS` 的保护在 deferred open 上仍存在绕过窗口。

建议：

1. 抽一个共享函数，例如 `_gate_and_dispatch_open_decision(candidate_or_decision)`。
2. 所有 open 决策，包括 main path、deferred_15m、deferred_pullback、deferred_chase，都必须先通过同一套 final slot gate。
3. 如果走 Ranking，进入 Ranker；如果明确不走 Ranking，也必须在 publish 前立即 reserve pending。
4. 补单测：
   - main 已满但 side slot 空，deferred main 必须 rejected。
   - low_rr slot 已满但 probe 空，deferred low_rr 必须 rejected。
   - pending probe 存在时 deferred probe 必须 rejected。
   - deferred selected 后 `_pending_open_slots[symbol]` 立即有记录。

### P1-1 `RANKING_ENABLED=false` 的直接发布路径仍没有 pending reservation

位置：

- `agents/trading/judge.py:1314-1378`
- `agents/trading/judge.py:1391-1393`
- `agents/trading/judge.py:1771-1782`

主 live path 已有 final slot gate；但当 `self._candidate_ranker.enabled` 为 false 时，代码不会进入 buffer，而是落到函数尾部直接 publish：

```python
await self.publish("trade_decision", decision, symbol=symbol)
if decision['action'] in ('open_long', 'open_short'):
    state['last_open_time'] = time.time()
```

它没有添加：

- `_pending_open_symbols`
- `_pending_open_slots`
- `_pending_open_ts`

这会导致 `_can_route_probe_short()` 新增的 pending probe 检查在 ranking disabled 模式下失效，因为 publish 后、execution_result 前，没有 pending probe 可检查。

默认 `RANKING_ENABLED=true` 能降低主路径风险，但 AC-PARAM-02 要求关闭新开关后行为可回滚且可控；`RANKING_ENABLED=false` 本身也是系统配置面，不能留下 slot 竞态。

建议与 P0-1 合并修：所有不经 Ranker 的 open publish 前也调用同一个 reserve helper。

## 5. 高优先级问题

### P1-2 Probe market eligibility 仍是 PRD 的近似版，不是验收版

位置：

- `utils/market_regime.py:91-134`
- `event_backtest.py:327-347`
- `test_regime_hysteresis.py:168-183`

PRD 要求 probe short 市场级条件至少满足以下之一：

- BTC 或 ETH 4h RSI 从 `>=75` 下穿 70，且当前 4h 为放量阴线。
- active_symbols 中 60% 以上 15m bias 从 bullish 转 neutral/bearish。
- TopN 24h breadth 仍 bullish，但最近 2h breadth 明显恶化。
- 资金费率极端偏多 + crowd 极端拥挤 + 15m 跌破关键均线。

当前实现是近似判断：

- 只看 `BTC-USDT`，没有 ETH。
- 只看当前 `60 < tf_4h_rsi < 70` 和 `volume_ratio > 1.5`，没有“上一根 >=75”、没有 downcross、没有阴线确认。
- 15m breadth 只看当前 bias 分布，不判断“从 bullish 转弱”。
- funding/crowd 条件没有 15m MA breakdown。
- event_backtest probe 触发更简化：bullish 中 weak short 且 `rsi >= 70` 即可能 probe，和 live 的 `_can_route_probe_short()` 不同构。

这不是误判：当前代码确实保留了早期反转通道，但它比 PRD 更宽，可能在 bullish 强趋势回调噪音中开 probe。

建议：

1. 在 RegimeManager 中保存至少上一轮 BTC/ETH 4h RSI、4h candle direction、15m breadth。
2. `is_probe_short_eligible()` 返回 `(allowed, reason)`，把 `probe_trigger_reason` 写入 attribution。
3. event_backtest 的 probe 触发逻辑与 live 同构，避免回测高估。
4. 补 ETH RSI、downcross、bearish candle、2h breadth、15m MA breakdown 的单测。

## 7. 系统维度审计

### Agent / flow

主链路现在是：

`multi_data_collector / tech_analyst` → `tech_analysis` → `Judge` → `trade_decision` → `Executor / PaperExecutor` → `execution_result / paper_execution_result` → `Judge / RiskGuard / PositionAnalyst / Reviewer`

优点：

- MessageBus 支持 symbol-scoped topic、优先级、背压、dead letter。
- `trade_decision` 和 `execution_result` 是 high priority。
- `paper_execution_result` 与 live `execution_result` 隔离，避免 paper 污染 live 状态。
- Judge 重启后会从 `positions.json` 恢复 `_open_positions`、slot、probe active。

风险：

- slot / pending 目前不是所有 open flow 的统一中间件能力，而是主路径局部逻辑；这就是 P0-1 / P1-1 的根因。
- 推荐把“开仓发布”收口成唯一函数，禁止各 flow 自己直接 publish open。

### LLM

位置：

- `agents/llm_client.py:19-87`
- `agents/llm_client.py:94-158`
- `agents/llm_client.py:231-302`
- `agents/trading/judge.py:960-1008`
- `agents/trading/judge.py:2460-2527`

优点：

- LLM JSON 有 schema 校验、默认值填充、action 白名单、confidence clamp。
- LLM 审计日志落盘到 `logs/llm_audit_YYYYMMDD.jsonl`。
- 有 prompt injection pattern 检测和 safety prefix。
- LLM 不可用时 Judge / Synthesizer / BehavioralCritic 都有规则降级。
- Judge 中 LLM 主要是修正因子；质量门、short guard、R:R、EV、15m、slot gate 仍在规则层。

风险：

- LLM reverse 在无 rule_signal 且 score 已过阈值时仍可改变方向；后续规则门会兜底，但 attribution 中建议更明确记录 `llm_overrode_direction=true`。
- LLM audit 只保存前 1000 字 user_msg 和 2000 字 raw_response；够追踪一般问题，但对长新闻上下文复盘可能不足。

### 接口回参 / attribution

已改善：

- Executor open result 会把 decision attribution 放入 payload 和 result。
- PaperExecutor open 会保留 attribution。
- Executor 外部平仓会透传 position attribution。
- CounterfactualLedger 事件已有 raw_regime、rr_policy、slot_type、blocked_by、is_probe、is_low_rr。

仍需补：

- PA close/reduce/add 的 attribution。
- deferred direct open 的 pending reservation 和 slot attribution 统一处理。
- probe eligibility 应写入明确触发原因，而不是只写 `is_probe=true`。

### 量化公式

当前核心公式总体自洽：

- risk budget：`margin=min(balance*10%, max_trade_amount)`，`max_loss=balance*5%`，杠杆按 SL 距离向下取 OKX 档位。
- cost model：手续费 + 资金费率方向性成本，EV 使用保守成本。
- EV：`p_win * net_profit - (1-p_win) * net_loss`，小样本走 Bayesian prior，rolling 样本足够后用真实胜率。
- rank score：signal / LLM relation / HTF / liquidity / RR / EV / entry_type 加权，low R:R 有 0.7 penalty。

主要公式风险不在 EV 本身，而在：

- event_backtest 的 probe 触发和 live 不同构。
- event_backtest 默认包含 live Phase 1 未上线的 partial TP / trailing。
- low R:R 和 probe 的 slot 约束没有作为统一 dispatch invariant。

## 8. 建议修复顺序

1. **先修 P0-1 / P1-1**：统一所有 open decision 的 final gate、Ranking、pending reservation。
2. 补 deferred slot/probe 的可证伪单测。
3. 收紧 probe market eligibility，并写入 `probe_trigger_reason`。
4. 调整 event_backtest Phase 1 验收默认行为，区分 live-faithful 和 enhanced。
5. 强化回测测试断言，避免 `assert True` 和永真断言。
6. 给 Phase 1 固定保护项加配置治理说明，避免被误当寻优参数。
