## 5. P1 问题

### P1-1：Ranking Top-N flush 可能一次性发布超过可用槽位的开仓

影响范围：并发持仓上限、实盘仓位暴露、同批多标的开仓。

证据：

- Judge 在正常 open path 中先通过 quality gate、EV、15m，再把 candidate 放入 ranker buffer 并 `return`：`agents/trading/judge.py:1107-1116`。
- flush 时只调用一次 `rank_and_select(self._open_positions)`：`agents/trading/judge.py:1152-1154`。
- 对 selected 列表逐个发布 open decision，但只更新 `state['last_open_time']`，没有更新 `_open_positions` 或预留 slot：`agents/trading/judge.py:1156-1164`。
- `_open_positions` 只有收到 `execution_result` 后才 add：`agents/trading/judge.py:314-317`。

风险：

如果当前 `_open_positions=0`，max slots=3，同一 flush buffer 中有 5 个候选，ranker 会选 3 个。问题在于这 3 个 open decision 会几乎同时发给 Executor；在交易所执行结果回来前，Judge 自身并不知道这些 slot 已被占用。若后续又有一批 candidate flush，仍可能按旧 `_open_positions` 计算可用槽位。更极端地，Executor 执行失败/成功的异步顺序也可能让 slot 状态滞后。

建议：

1. 增加 `_pending_open_symbols` 或 `_reserved_open_slots`，ranking selected 后立即预占。
2. `rank_and_select()` 的 available slots 应使用 `len(_open_positions | _pending_open_symbols)`。
3. 收到 `execution_result` 成功、失败、rejected 后释放或确认 pending。
4. 增加测试：max=3，已有2仓，同一窗口3个候选，最终只发布1个 open，其余 hold。
5. 增加测试：selected 发布后、execution_result 未回来前，新候选不得再占用同一 slot。

### P1-2：新增账单 PnL 对账模块 API 失败时 fail-open，且未接入运行路径

影响范围：真实 PnL 对账、账本可信度、未来定时告警。

证据：

- `utils/reconciliation.py` 新增 `Reconciler`，用于比对 OKX bills 与本地 ledger。
- `check_recent_bills()` 捕获异常后只记录 warning，最终返回 `[]`：`utils/reconciliation.py:83-87`。
- `run_and_report()` 将空列表视为无差异并返回 `None`：`utils/reconciliation.py:96-100`。
- 当前代码里除测试外没有运行路径引用该 `Reconciler`：全局搜索仅测试引用。

风险：

如果后续把这个模块接到 Telegram 或定时任务，OKX 账单 API 异常会被解释成“无差异”，形成 PnL 对账 fail-open。虽然它目前未接入实盘流程，不会影响 `/resume`，但作为新增模块，语义需要在接入前修正。

建议：

1. `check_recent_bills()` 返回结构化结果，例如 `{status: ok|error, mismatches: [], query_ok: bool}`。
2. API 异常时 `run_and_report()` 返回告警文本，而不是 `None`。
3. 测试 `test_api_failure_graceful` 不应断言 `[]`，应断言 error 状态。
4. 接入定时任务前明确和 `PositionReconciler` 的职责边界：持仓恢复用 fail-closed，账单差异用 warning/error。

### P1-3：`record_add()` 未被测试覆盖，且 lifecycle 没有维护加仓后的持仓口径

影响范围：加仓后 lifecycle 审计、平均入场价、总保证金、后续 reduce/close 口径。

证据：

- `LiveLedger.record_add()` 会写 `event_type="add"` 并调用 `_update_lifecycle_pnl()`：`utils/live_ledger.py:56-86`。
- `_update_lifecycle_pnl()` 只追加 events、PnL 和 fee，不更新 entry price、total amount、avg entry：`utils/live_ledger.py:310-320`。
- 现有测试搜索不到 `record_add` 或 add lifecycle 用例。
- `executor.add_to_position()` 已改为调用 `record_add()`：`executor.py:1235-1244`。

风险：

主问题“加仓不应新建 lifecycle”已经修了，但 lifecycle 仍无法表达加仓后的真实持仓规模和加权均价。后续 close 的 PnL 仍依赖 Executor position 的 entry_price，而不是 ledger lifecycle，因此账本和执行器状态仍可能分叉。

建议：

1. 给 lifecycle 增加 `total_amount_usdt`、`avg_entry_price`、`adds_count`。
2. `record_add()` 更新加权均价和总保证金。
3. 增加 `open -> add -> reduce -> close` 测试，断言只有一个 lifecycle，events 包含 `open/add/reduce/close`。
4. 增加 add 后 close 的 PnL 与预期一致性测试。
