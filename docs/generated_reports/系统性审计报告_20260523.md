审计日期：2026-05-23  
审计对象：`crypto-arbitrage` 多 Agent 加密货币趋势交易系统  
审计目标：以“可控实盘风险 + 可复盘正期望闭环”为最终目标，系统性检查系统层、架构层、Agent/LLM、消息接口回参和主要业务 flow。

## 1. 执行摘要

当前项目已经不是最初的跨交易所套利系统，而是一个以 OKX USDT 永续合约为主执行场所的多 Agent 趋势交易系统。系统工程化程度明显高于原型项目：主入口清晰、Agent 分层明确、消息总线具备优先级/背压/DLQ、风控与执行链路已有大量回归测试，且 LLM 不可用时多数关键路径能降级到规则逻辑。

本轮审计基线：

- 全量测试结果：`469 passed, 4 deselected, 1 warning in 196.55s`。
- 默认 pytest 排除 `network` 标记测试；真实 OKX/Telegram 冒烟仍依赖网络、凭证和人工确认。
- 代码质量整体可继续 paper、mock、testnet 验证；不建议在修复 P0 前扩大 live 仓位或并发。

核心结论：

1. 系统方向是合理的：用 Research 层选标的，用 Trading 层做多维度采集、技术分析、Judge 决策、执行和复盘，符合 Hummingbot V2、QuantConnect Algorithm Framework、NautilusTrader 等成熟框架的职责拆分思路。
2. 当前最大风险不是“缺少功能”，而是复杂链路中少数字段契约、状态所有权和交易所订单生命周期还没有完全收敛。
3. P0 必须优先处理：Bucketed EV 的 short side 传播缺口、全局 halt/resume 状态所有权分裂、`execution_result.v2` 发布契约未完全统一。

## 2. 对标框架与辩证结论

“没有最优，只有最适合”。本项目是单进程、小账户、低并发、研究驱动型 crypto 合约交易系统，不需要照搬重型机构框架；但成熟框架能帮助识别哪些工程边界不能省。

| 对标对象 | 关键设计 | 对本项目的校验结论 |
|---|---|---|
| Hummingbot V2 | Controller 产生信号，Executor 管理订单/仓位生命周期 | 本项目 `TechAnalyst/Judge` 与 `MultiExecutor/ContractExecutor` 的分离方向正确；但订单生命周期，尤其 OKX 附带 TP/SL 与本地 trailing，应继续收敛为单一所有者。 |
| QuantConnect LEAN Algorithm Framework | Alpha、Portfolio Construction、Execution、Risk 分离 | 当前 Alpha/Judge/Execution/Risk 已具雏形；Portfolio Construction 仍散落在 Judge ranking、risk budget、slot gate 中，后续可抽为显式模块。 |
| NautilusTrader | 事件驱动、强类型 order/execution/risk 事件 | 本项目 in-process dict message bus 适合当前规模；关键交易事件仍需要更强 schema 和持久事件日志。 |
| Freqtrade | Protections、StoplossGuard、stoploss on exchange、trailing stop | 本项目已有 escalating cooldown、exchange stop、local trailing；但 exchange-side algo order 与本地止损变更的同步要测试到交易所语义层。 |

| CCXT / OKX API | unified API 加 exchange-specific params；OKX TP/SL attach algo 参数强交易所相关 | mock 只能证明参数传递，不能证明交易所接受和生命周期正确；OKX testnet/小额 live 前必须做语义验收。 |

## 3. 当前系统画像

### 3.1 入口与生命周期

主入口是 `run_agents.py`，核心编排在 `agents/orchestrator.py`：

- `Orchestrator._register_agents()` 注册 6 个 Research agents 和 10 个 Trading agents。
- `MessageBus.reset()` 后所有 Agent 共享单进程消息总线。
- `_research_loop()` 首次启动 5 秒后触发研判，之后定时或 idle 提前触发。
- `_command_listener()` 监听 `system_command` 和非 hold `trade_decision`，用于远程 shutdown 与活跃度统计。
- `_graceful_shutdown()` 停止 Agent、取消 task、保存状态、关闭总线。

系统是单进程 asyncio 架构，适合当前低并发交易规模。风险是进程崩溃时内存消息丢失，不具备跨进程恢复能力。

### 3.2 两层 Agent 架构

Research 层：

```text
research_trigger
  -> MarketScanner
  -> SentimentResearcher
  -> NewsResearcher
  -> ResearchSynthesizer
  -> Censor
  -> ResearchSynthesizer final
  -> SymbolRouter
  -> symbol_update
```

Trading 层：

```text
symbol_update
  -> MultiDataCollector
  -> market_data / price_tick / news_snapshot
  -> MultiTechAnalyst
  -> tech_analysis
  -> MultiJudge
  -> trade_decision.v2
  -> MultiExecutor / PaperExecutor
  -> execution_result.v2 / paper_execution_result
  -> Reviewer / PortfolioRiskGuard / PositionAnalyst / TelegramNotifier
```

持仓管理旁路：

```text
execution_result + tech_analysis + price_tick
  -> PositionAnalyst
  -> position_review
  -> BehavioralCritic
  -> position_verdict
  -> PositionAnalyst arbitration
  -> trade_decision close/reduce/add
```

## 4. 系统层审计

### 4.1 配置与启动安全

优点：

- `utils/config_loader.py` 采用 `defaults -> config.yaml -> env` 的覆盖顺序。
- `load_config(strict_live_check=True)` 在 live 模式缺少 OKX/Binance 凭证时拒绝启动。
- `_validate_hard_limits()` 对关键风控参数做硬范围校验。
- `format_banner()` 启动时输出关键风险参数，有利于人工确认。

风险：

- `.env.example:5` 默认 `USE_TESTNET=false`。虽然 live 缺凭证会拒绝启动，但复制 `.env.example` 后填入真实凭证就进入实盘模式。对当前项目阶段，默认 testnet 更符合安全优先。
- `README.md` 的当前实盘参数写 `MAX_TRADE_AMOUNT=30`，`.env.example` 默认是 `10.0`，`config.yaml` 是 `500`。虽然 env 优先级明确，但文档/配置漂移会造成误判。
- `config.yaml` 仍保留套利字段和较大的 `risk.max_trade_amount: 500`，与当前趋势系统主路径不完全一致。

建议：

- P1：把 `.env.example` 改为 `USE_TESTNET=true`，live 运行要求额外 `LIVE_ACK=I_UNDERSTAND` 或等价确认。
- P1：把 README、runbook、config.yaml 中的当前实盘口径统一，保留历史套利配置时明确标注“归档/非主路径”。

### 4.2 消息总线与可靠性

优点：

- `agents/message_bus.py` 有消息优先级：critical risk/halt 高于 trade decision/execution result，高于分析数据。
- 队列有 soft/hard 背压，并对低优先级消息丢弃。
- 有 dead letter 和 metrics 快照。

风险：

- 总线是进程内 `asyncio.PriorityQueue`，没有 durable event log。进程崩溃时，已发布未消费的 `trade_decision`、`execution_result`、`system_command` 会丢失。
- 消息是 dict，没有集中 schema registry。随着 flow 增多，字段缺失只能靠下游兼容和测试兜底。

建议：

- P1：给 critical topics 做最小事件 journal：`trade_decision.v2`、`execution_result.v2`、`daily_hard_stop_triggered`、`system_command`。
- P1：新增轻量 schema registry 或 dataclass/pydantic adapter；不需要重写全系统，先覆盖交易关键消息。

### 4.3 Agent 运行监督

优点：

- `BaseAgent._message_loop()` 和 `_periodic_loop()` 都捕获异常并继续运行，单次消息失败不会杀死整个 Agent。
- Orchestrator 能优雅停机并保存状态。

风险：

- `BaseAgent.run()` 中 `setup()` 在创建 message/tick loop 前执行，setup 阶段失败会让该 Agent task 退出；Orchestrator 当前没有单 Agent supervisor/restart 策略。
- MessageBus metrics 已存在，但默认没有形成健康检查、告警阈值或自动恢复动作。

建议：

- P2：Orchestrator 增加 Agent task health 监控，记录 setup/tick/message loop 状态。
- P2：Telegram `/status` 或 health endpoint 增加 queue size、dropped、DLQ、LLM degraded、data degraded 状态。

## 5. 架构层审计

### 5.1 职责边界

整体职责划分合理：

- Research 层负责候选池。
- DataCollector 负责多频率数据采集。
- TechAnalyst 负责“看到什么”，不直接下交易建议。
- Judge 负责“是否交易、如何交易”。
- Executor 负责下单、仓位同步、止损止盈。
- Reviewer 负责复盘与 EV/分桶胜率反馈。
- PortfolioRiskGuard 与 RiskManager 负责组合和账户级风险。

主要问题：

- Portfolio construction 隐式散落在 Judge 的 risk budget、ranking、slot gate、probe/low_rr 逻辑里。当前可以接受，但随着策略复杂度上升，后续应抽出显式 `PortfolioConstruction` 或 `PositionAllocator`。
- `execution_result` 既承担订单执行回报，又承担风险强平、外部平仓、同步发现、减仓回报，语义过宽。必须依赖统一字段稳定下游。

### 5.2 数据源语义

系统执行场所是 OKX，但部分 crowd/OI/taker/long-short 信号来自 Binance 公共接口或 RSS/第三方数据：

- `MarketScanner._fetch_long_short_ratio()` 使用 Binance top trader long/short ratio。
- `MultiDataCollector` 的 taker、big trades、long-short 等维度存在跨源组合。

这不是错误。成熟交易系统经常混合数据源；问题在于必须显式记录 provenance 和 confidence，避免把 Binance 市场结构直接当成 OKX 可执行盘口事实。

建议：

- P1：给 `market_data` 的跨源字段增加 `source`、`freshness_sec`、`available`、`confidence`。
- P2：Reviewer 分桶中增加 “数据质量/数据源可用性” 维度，判断某类信号是否真的贡献正期望。

## 6. Agent 与 LLM 审计

### 6.1 LLMClient

优点：

- `LLMClient.chat_json()` 自动追加安全前缀，要求 JSON 输出。
- 有 prompt injection pattern 检测和用户输入截断。
- 有 JSON 解析、可选 schema 校验、审计日志 `logs/llm_audit_YYYYMMDD.jsonl`。
- LLM 不可用时抛 `LLMUnavailableError`，多数调用方有规则降级。

风险：

- 只有 Judge 明确传入 `JUDGE_DECISION_SCHEMA`。`SYNTHESIS_SCHEMA` 虽定义但 ResearchSynthesizer 未使用；Censor、TechAnalyst、BehavioralCritic 也主要依赖自由 JSON。
- LLM audit log 写入 `user_msg` 前 1000 字、`raw_response` 前 2000 字和 parsed 结果。当前主要是市场数据，但未来若加入账户/仓位敏感信息，需要脱敏和保留策略。
- 默认模型名 `claude-opus-4-6` 由 env 决定；需要确认中转站模型名真实可用，否则会静默进入规则降级。

建议：

- P1：给 ResearchSynthesizer、Censor、TechAnalyst、BehavioralCritic 均补 schema。
- P1：LLM audit 增加字段级脱敏、保留天数、是否记录原始 prompt 的配置开关。
- P2：将 `llm_degraded` 进入 Telegram/health 状态，而不是只在日志中可见。

### 6.2 Judge

优点：

- Judge 是当前系统决策核心：融合规则评分、LLM、R:R、EV、15m 入场确认、regime、ranking、slot gate、request_id。
- `_gate_and_publish_open()` 统一生成 `request_id` 和 `schema_version=trade_decision.v2`，方向正确。
- EV 门引入 rolling/bayesian/bucketed win rate，符合“用复盘数据反哺决策”的正期望目标。

P0 风险见 F-001：Bucketed EV 的 side 传播缺口。

### 6.3 Executor / Risk / Reviewer

优点：

- Executor 下单前有余额、风控、持仓冲突、幂等、防滑点、订单能力预检。
- ContractExecutor 支持 OKX attach TP/SL，并本地维护 positions。
- Reviewer 将执行结果回写历史，并给 Judge 提供 rolling/segmented metrics。

风险：

- `execution_result.v2` 存在 helper，但早期拒绝/error 路径仍有 inline payload，字段不完全一致。
- OKX attached TP/SL 与本地 trailing/partial close/加仓后重算 SL 的生命周期需要继续验证。
- Reviewer 只订阅 `execution_result`，PaperExecutor 的 `paper_execution_result` 不自动进入同一复盘闭环。

### 7.2 契约层总体判断

当前消息契约已足以支撑本地和 testnet 迭代，但还没有达到“可放心扩 live”的程度。原因是最关键的两个 topic，`trade_decision.v2` 与 `execution_result.v2`，还存在 legacy 分支和字段不完全一致的发布路径。对小仓位 paper/live shadow 可以接受；对扩大实盘风险不够。

## 8. Flow-by-flow 审计

### Flow 1：启动与配置

路径：

```text
run_agents.py
  -> load_config()
  -> Orchestrator.start()
  -> MessageBus.reset()
  -> register agents
  -> agent.run()
```

结论：可用。硬限制和 live 凭证校验是正确方向。主要风险是 `.env.example` 默认 live 和配置/文档漂移。

### Flow 2：Research 选币

路径：

```text
research_trigger
  -> market/sentiment/news 三路数据
  -> synthesizer preliminary
  -> censor challenge
  -> synthesizer final
  -> symbol_router
```

结论：架构合理，符合“研究层慢频选候选池，交易层快频执行”的思路。风险是 LLM schema 未统一、cycle 结果不是完全对象化、跨数据源质量未进入最终字段。

### Flow 3：标的路由与轮换

路径：

```text
research_result -> symbol_update
removed symbols -> trade_decision close
```

结论：清晰。需要注意 removed 直接 close_at_market 是策略选择，不是通用最优；在小账户趋势系统中可接受，但应在回测/paper 中验证是否过度换手。

### Flow 4：行情采集

路径：

```text
symbol_update -> MultiDataCollector
10s price_tick
30s orderbook/liquidation
60s market_data
300s 4h/1d
30min news_snapshot
```

结论：覆盖面好。`data_quality.degraded` 是关键保护。建议后续把跨交易所字段来源显式化。

### Flow 5：技术分析

路径：

```text
market_data -> indicators/rule_signal/LLM summary -> tech_analysis
```

结论：TechAnalyst 职责边界正确，只输出观察，不直接发交易。LLM 部分需要 schema 化，否则异常 JSON 只能靠 fallback 和下游容错。

### Flow 6：Judge 决策

路径：

```text
tech_analysis
  -> rule score
  -> LLM decision / fallback
  -> stop/tp/risk budget plan
  -> R:R gate
  -> EV gate
  -> 15m timing
  -> ranking/slot gate
  -> trade_decision.v2
```

结论：这是系统复杂度最高、同时也是最需要严格契约的 flow。当前 open 主链路的 request_id、attribution、slot gate 方向正确；但 Bucketed EV short side 缺口是 P0。

### Flow 7：实盘执行

路径：

```text
trade_decision -> MultiExecutor
  -> halt/risk/balance/precheck/idempotency
  -> ContractExecutor.open_position_with_plan()
  -> OKX order + attachAlgoOrds
  -> positions.json
  -> execution_result.v2
```

结论：下单前保护比较完整。主要风险是 `execution_result` 契约碎片化和 OKX attach TP/SL 后续生命周期。

### Flow 8：Paper 执行

路径：

```text
trade_decision -> PaperExecutor -> paper_execution_result
```

结论：与 live 隔离是正确的，避免 paper 污染真实仓位。缺口是 paper 结果没有自动进入 Reviewer 的同一套 EV/segmented metrics，只能作为独立影子账户看待。

### Flow 9：风控、熔断与恢复

路径：

```text
Reviewer daily hard stop -> daily_hard_stop_triggered
PortfolioRiskGuard risk_alert -> Executor emergency close
Telegram /halt /resume -> system_command
HaltState persisted state
```

结论：风控覆盖面好，但 halt/resume 状态所有权分裂是 P0。恢复交易必须由一个 owner 完成持久状态和本地状态更新。

### Flow 10：持仓管理

路径：

```text
execution_result/tech_analysis/price_tick
  -> PositionAnalyst
  -> position_review
  -> BehavioralCritic
  -> position_verdict
  -> trade_decision close/reduce/add
```

结论：持仓管理引入批判官是合理的，有助于减少过早止盈、亏损厌恶、恐慌平仓等行为偏差。风险是 PA 生成的 close/reduce/add 决策仍偏 legacy，缺少与 Judge open 主链路同级别 request_id/schema。

### Flow 11：复盘与 EV 闭环

路径：

```text
execution_result -> Reviewer
  -> trade_history
  -> rolling metrics
  -> segmented metrics
  -> strategy_review -> Judge
```

结论：这是项目迈向正期望系统的关键闭环。当前方向正确。风险是 daily PnL UTC/local 时间口径不一致，以及 paper/live 指标未形成自动对照。

### Flow 12：运维与观测

路径：

```text
logs + llm_audit + message_bus metrics + Telegram commands
```

结论：已有基础观测，但缺少统一 health supervisor。下一阶段应把“Agent 是否活着、队列是否堆积、数据是否 degraded、LLM 是否 degraded、halt state 是否一致”作为可见状态。

## 13. 最终判断

当前项目的工程底座是可继续推进的。469 条测试通过说明主链路已有相当覆盖，Research/Trading 两层 Agent 架构也符合成熟交易框架的方向。

但当前不应把“测试多”误读为“可扩 live”。交易系统真正危险的地方通常不是大面积功能缺失，而是少数关键契约字段、状态所有权和交易所真实语义在边界条件下不一致。本轮审计发现的 P0 都属于这类问题。

建议状态：

- 本地开发：可以继续。
- Paper：可以继续。
- Mock/testnet：可以继续，并应重点覆盖 P0/P1。
- 小额 live：仅在当前已有风控额度内谨慎运行。
- 扩大 live 仓位或并发：等待 P0 全部修复并通过回归。

最终目标不是追求抽象最优架构，而是建立一个能解释每笔交易、能限制最坏损失、能从复盘中持续更新胜率假设的正期望系统。按这个目标看，下一阶段最重要的不是继续加 Agent，而是把现有关键 flow 的契约、状态和交易所语义压实。
