# 系统性代码审计报告（2026-05-28）

## 0. 审计口径

本次审计目标是验证当前多 Agent OKX 趋势交易系统是否具备更大 live 扩容条件。审计范围覆盖系统层、架构层、Agent flow、LLM 契约、执行接口回参、OKX 条件单语义、测试体系和文档事实一致性。

审计基准假设：项目最终目标不是抽象上的最优架构，而是稳定、可解释、风险边界清晰、适合小额到逐步扩容的 OKX USDT 永续趋势交易系统。

对标原则：
- Freqtrade 类框架对 exchange-side stoploss 的核心要求是明确 owner、可控更新频率、异常时保守处理。
- Hummingbot Controller/Executor 模式强调策略决策与订单生命周期分离，订单生命周期应由 executor 持有。
- LangGraph 类 durable flow 思路可作为长期对标：关键 flow 的状态与恢复点必须可追踪、可重放、可恢复。

结论先行：当前默认自动化回归为绿，适合继续小额 live 灰度；但不建议在 P1 执行语义问题修复前扩大 live。

结果：

## 2. P1 Findings

### F-001: EarlyReview 直接修改本地 SL，绕过交易所保护单替换

位置：`agents/trading/executor.py:758-780`

`_early_review()` 在持仓前 30 分钟内达到规则条件时，直接修改 `pos['stop_loss']`、写入 `self.executor.positions` 并 `_save_positions()`。该路径没有调用根执行器 `_replace_protective_sl()`。

影响：
- 本地状态显示 SL 已收紧，但 OKX exchange-side protective SL 仍可能停留在旧价格。
- 若进程崩溃、本地轮询失败、网络抖动或同步延迟，实际保护弱于本地状态。
- 这违反当前文档宣称的 “SL cancel/place 单一入口” 目标。

建议：
- `_early_review()` 不应直接改 `pos['stop_loss']` 后保存。
- 应调用根执行器 `_move_sl()` 或 `_replace_protective_sl()`，由根执行器统一更新 `sl_algo_id/sl_sync_state/protection_state`。
- 增加测试：early review 收紧 SL 时必须调用 `_replace_protective_sl()`，且 cancel/place 失败时不得只保存本地 SL。

### F-002: `_replace_protective_sl()` 忽略旧 SL 撤单失败

位置：`executor.py:1120-1195`

`_replace_protective_sl()` 调用 `_cancel_protective_sl(symbol, position)` 后不检查返回值，继续 `_place_protective_sl()`。如果 OKX 旧 algo 撤单失败，仍会挂新 SL。

影响：
- 交易所可能同时存在旧 SL 和新 SL。
- 本地 `sl_algo_id` 指向新单，但旧单仍可能触发。
- 多保护单场景在重启迁移中会被视为异常，但 live 运行时已经可能暴露风险。

现有测试缺口：
- `test_partial_tp_lifecycle.py` 覆盖了新 SL 挂单失败会置 unknown/halt。
- 没有覆盖 “cancel old SL failed, should not place new SL”。

建议：
- 如果 `_cancel_protective_sl()` 返回 False，应立即：
  - `sl_sync_state='failed'`
  - `protection_state='unknown'`
  - live OKX 下 `_halt_symbol(symbol, reason='sl_cancel_failed')`
  - 返回 False，不继续挂新 SL。
- 增加 cancel failure 回归测试。

### F-003: Agent 层多条 close 路径仍直接 `cancel_order()`，绕过 OKX trigger-algo 语义

位置：
- `agents/trading/executor.py:219-221`
- `agents/trading/executor.py:367-370`
- `agents/trading/executor.py:390-393`
- `agents/trading/executor.py:412-415`
- `agents/trading/executor.py:464-467`
- `agents/trading/executor.py:679-682`
- `agents/trading/executor.py:713-716`

这些路径在 close 前直接 `self.executor.cancel_order(symbol, sl_order_id)`，而根执行器已验证 OKX trigger algo 需要走 `cancel_orders([id], symbol, params={'trigger': True})`。直接 `cancel_order()` 对 OKX algo 语义不一致。

影响：
- 风控强平、全平、本地 stop fallback 等关键路径可能无法正确取消 OKX SL algo。
- close 成功后可能残留 orphan algo。
- 与 `_cancel_protective_sl()` 单一入口设计冲突。

建议：
- Agent 层不直接取消保护单。
- 全平应调用根执行器 `close_position()`，由根执行器负责保护单清理。
- 如必须显式取消，应暴露根执行器公共方法 `cancel_protective_sl()`，内部统一转 `_cancel_protective_sl()`。
- 所有 execution_result contract 测试需要从 “是否调用 cancel_order” 改为 “是否调用 OKX-aware protective cancel 或由 close_position 接管”。

### F-004: `force_closed` 被 Judge 无条件计入 SL hit

位置：`agents/trading/judge.py:406-421`

Judge 对所有 `status == 'force_closed'` 都调用 `_record_sl_hit()`。但 `force_closed` 来源包括 risk alert、daily hard stop close_all、price_fetch_failed、本地 stop_loss 等，并不等同于策略止损。

影响：
- escalation cooldown 被风控强平、人工/系统全平、价格获取失败污染。
- `last_sl_direction` 可能错误，影响同方向/反方向冷却判断。
- 后续策略表现评估会把非策略 SL 误记为策略失败。

建议：
- `execution_result.v2` 增加或规范 `exit_reason` / `close_cause`。
- Judge 只在 `reason in ('stop_loss', 'exchange_sl', 'local_stop_loss')` 或明确亏损 SL 事件时 `_record_sl_hit()`。
- 对 `risk_alert`、`close_all`、`daily_hard_stop`、`price_fetch_failed` 走独立 cooldown 或不进入 SL 递增冷却。

## 3. P2 Findings

### F-005: BehavioralCritic schema 与 prompt/consumer 字段不一致

位置：
- `agents/llm_client.py:114-120`
- `agents/trading/behavioral_critic.py:50-59`
- `agents/trading/behavioral_critic.py:185-192`
- `agents/trading/position_analyst.py:538-545`

Schema 要求 `counter_action/confidence`；prompt 和 fallback 输出 `counter_recommendation/confidence_in_challenge`；PositionAnalyst 读取 `counter_recommendation`。

当前能工作主要依赖 `validate_against_schema()` 透传额外字段。这不是严格契约。

建议：
- 统一字段名，推荐保留业务语义更清晰的 `counter_recommendation` / `confidence_in_challenge`。
- 或 PA 同时兼容两套字段，但 schema/prompt/fallback 测试必须覆盖。

### F-007: `network` 测试体系不可重复

- `test_indicators.py:8-20`

问题：

### F-008: testnet 与 live 共用状态文件的运行入口风险仍需明确

位置：
- `agents/trading/executor.py:35-42`
- `executor.py:34`
- `risk_manager.py:21`
- `utils/live_ledger.py:17-18`

`verify_okx_testnet_real.py` 使用独立 `data/testnet_positions.json`，但 `run_agents.py` 在 `USE_TESTNET=true` 时仍默认使用：
- `data/positions.json`
- `data/risk_state.json`
- `data/live_order_events.jsonl`
- `data/live_position_lifecycle.json`

影响：
- 如果用 `run_agents.py` 跑 testnet/paper 验收，可能污染 live 状态与 ledger。
- 多 Agent 读 `data/positions.json` 的路径较多，状态命名空间未完全隔离。

建议：
- 引入 `STATE_NAMESPACE=live|testnet|paper` 或由 config 生成状态文件前缀。
- 所有 Agent 读取持仓状态应从配置拿路径，而不是硬编码 `data/positions.json`。

### F-009: Agent health supervisor 仍未落地

位置：
- `agents/base.py:48-64`
- `agents/orchestrator.py:117-123`
- `docs/to-do-list.md:30`

现状有 research watchdog，但没有统一 agent health supervisor。Agent setup 失败、消息 loop 停止、队列堆积、DLQ 增长、LLM degraded、data degraded 仍无法形成统一健康状态。

建议：
- Orchestrator 记录每个 task 的 setup/result/last_tick/last_message。
- Telegram `/status` 展示 queue backlog、DLQ、agent degraded 状态。

### F-010: 新闻 symbol mention 使用 substring，短 ticker 易误报

位置：
- `agents/research/news_researcher.py:108-124`
- `agents/trading/multi_data_collector.py:223-233`

当前用 `if symbol in text or f"${symbol}" in text`。短 symbol 如 `STX`、`OP`、`INJ` 容易匹配普通英文片段。

建议：
- 使用 token boundary / `$SYMBOL` / `(SYMBOL)` / `SYMBOL token` 白名单匹配。
- 给新闻信号加入 `source/freshness_sec/confidence`，避免弱新闻信号被当成强事实。

## 4. 架构判断

当前系统已经形成较完整的两层 Agent flow：

```text
research_trigger
  -> MarketScanner / SentimentResearcher / NewsResearcher
  -> ResearchSynthesizer
  -> Censor
  -> SymbolRouter
  -> symbol_update
  -> MultiDataCollector
  -> TechAnalyst
  -> Judge
  -> trade_decision.v2
  -> MultiExecutor / PaperExecutor
  -> execution_result.v2
  -> Reviewer / RiskGuard / PositionAnalyst / Telegram
```

优势：
- 主入口已统一为 `run_agents.py`。
- open 主路径基本收敛到 `trade_decision.v2`。
- 默认测试覆盖面明显提升。
- OKX posMode、contract size、R:R floor、Long Entry Guard、partial TP lifecycle 都已有专项测试。
- LLM 不可用时多数关键路径可规则降级。

主要不足：
- 执行层还有 Agent 与根 executor 混合持有订单生命周期的问题。
- `execution_result.v2` 是统一了字段，但 close cause 语义还不够精细。
- 真实 testnet 验收支撑小额灰度，但还不足以支撑无 caveat 扩容。
- 测试套件中 legacy network 用例降低了“全量验证”的可信度。

## 5. 建议修复顺序

1. 修复 F-001/F-002/F-003：保护单生命周期必须由根 `ContractExecutor` 单一 owner 管理。
2. 补测试：early review SL 替换、cancel failure 不重挂、所有 close path 不直接 `cancel_order()`。
3. 修复 F-004：区分 SL hit、风控强平、外部平仓、系统全平，避免 cooldown 污染。
4. 修复 F-005：BehavioralCritic 字段契约统一。
5. 调整 testnet 报告和 Go/No-Go 文案：`7 PASS / 3 SKIP` 支持小额灰度，不等于无 caveat 扩容。
6. 整理 network 测试，把无限脚本和依赖本地 DB 的脚本移出默认验收语义。
7. 做状态命名空间和 Agent health supervisor。

## 6. Go/No-Go

| 场景 | 判断 | 原因 |
|---|---|---|
| 本地开发 | GO | 默认回归通过，代码可继续迭代 |
| paper/mock | GO | 核心 mock/contract 测试通过 |
| 小额 live 灰度 | CONDITIONAL GO | OKX testnet 关键 long_short_mode 路径已通过，但需接受 P1 风险并保持小额 |
| live 扩容 | NO-GO | 保护单生命周期仍有 owner 分裂与 cancel failure 风险 |

最终判断：当前系统不是“不行”，而是已经进入需要严控执行语义的阶段。下一步不要继续堆策略或 Agent，先把 OKX 保护单生命周期和 close cause 语义压实。
