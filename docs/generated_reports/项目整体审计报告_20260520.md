```text
run_agents.py
```

### P0-2：Telegram 对账使用错误凭证变量，恢复流程可能失效

严重级别：`High`  
影响范围：`/resume`、`/reconcile`、熔断恢复  
证据：

- 项目统一使用 `OKX_PASSWORD`：README、config loader、Executor、Judge、DataCollector 均如此。
- `agents/trading/telegram_notifier.py:401-405` 使用的是 `OKX_PASSPHRASE`：

```python
'password': os.environ.get('OKX_PASSPHRASE', '')
```

风险：

- Telegram `/resume` 会先执行对账；对账 exchange 可能因缺 password 而无法拿到真实持仓。
- 在熔断恢复时，系统可能误判“对账失败”或因 exchange 为半初始化对象而产生错误。

建议：

1. 改为 `OKX_PASSWORD`，兼容可选读取 `OKX_PASSPHRASE` 作为旧别名。
2. 对账 exchange 初始化失败时应明确返回 mismatch/error，而不是静默 `pass`。
3. 给 `/resume`、`/reconcile` 加单测覆盖凭证变量。

### P0-3：四方持仓对账 symbol 未统一，可能产生误报/漏报

严重级别：`High`  
影响范围：熔断恢复、人工运维判断  
证据：

- `PositionReconciler._fetch_exchange_positions()` 返回交易所原始 symbol，例如 `BTC/USDT:USDT`。
- Executor 本地持仓通常是 `BTC-USDT-SWAP`。
- `reconcile()` 直接用 set 比较 `exchange_symbols` 和 `executor_symbols`，没有在比较前统一格式。

风险：

- 交易所与 Executor 明明是同一持仓，也会被判定为 `missing_in_executor` / `missing_in_exchange`。
- 真实不一致也可能因为某些格式碰巧被绕过。

建议：

1. 对所有参与比较的 symbol 使用 `utils.symbol.to_internal()`。
2. 对账结果保留原始 symbol 和 normalized symbol 两列。
3. 增加 OKX `BTC/USDT:USDT` vs 本地 `BTC-USDT-SWAP` 的单测。

### P0-4：Judge 关键运行态不持久化，重启后并发持仓限制与冷却会失效

严重级别：`High`  
影响范围：并发持仓上限、SL 冷却、延迟入场、重复开仓保护  
证据：

- `agents/trading/judge.py` 中 `_open_positions`、`_symbol_state`、`deferred_entry`、`sl_timestamps` 都是内存态。
- `PositionAnalyst` 和 `RiskGuard` 会从 `data/positions.json` 补录持仓，但 `Judge` 启动时没有从 `positions.json` 恢复 `_open_positions`。

风险：

- 系统重启后，Judge 认为当前 active positions 为空，可能继续发布新开仓决策，突破 `max_concurrent_positions`。
- 同标的 SL 递增冷却、强平冷却、延迟入场状态丢失。
- Executor 会拒绝同标的已有持仓开仓，但无法阻止跨标的并发上限被绕过。

建议：

1. Judge `setup()` 从 `data/positions.json` 恢复 `_open_positions`。
2. 将 `_symbol_state` 的关键字段原子写入 `data/judge_state.json`。
3. `symbol_update` 和 `execution_result` 统一用 `to_internal()`，保证恢复状态可比对。

### P0-5：BaseAgent 调度模型会被 tick sleep 阻塞，关键消息可能延迟处理

严重级别：`High`  
影响范围：Executor、Reviewer、Telegram、PaperExecutor、RiskGuard 及时性  
证据：

`BaseAgent.run()` 每轮只处理一条消息，然后执行 `await self.tick()`。很多 Agent 的 `tick()` 内有固定 sleep：

- `ReviewerAgent.tick()` sleep 60 秒
- `PaperExecutor.tick()` sleep 30 秒
- `MultiExecutor.tick()` sleep 5 秒
- `PortfolioRiskGuard.tick()` sleep 10 秒
- `TelegramNotifier.tick()` poll 后 sleep 5 秒

风险：

- 高优先级消息进入 PriorityQueue 后，如果该 Agent 正在自己的 `tick()` sleep，仍然要等 sleep 结束才会处理。
- Reviewer 可能延迟处理 execution_result 和 Daily Hard Stop 检查。
- Executor 可能延迟处理 risk_alert / daily_hard_stop。

建议：

1. 将消息消费与周期任务拆成两个独立 asyncio task。
2. `tick()` 不应长期 sleep；周期控制应通过 `next_run_at` 判断。
3. 对 `daily_hard_stop_triggered -> executor close_all` 增加最大延迟测试。

### P1-1：研判层数据聚合存在竞态，可能只用 market data 做初选

严重级别：`Medium-High`  
影响范围：研判质量、新闻否决、情绪输入  
证据：

`ResearchSynthesizer.on_message()` 在收到 `research_market_data` 后立即 `_preliminary_synthesis()`，不等待 `research_sentiment_data` 和 `research_news_data`：

```python
if 'research_market_data' in self._pending_data:
    await self._preliminary_synthesis()
```

随后 `_pending_data.clear()`。

风险：

- MarketScanner 较快返回时，Sentiment/News 尚未完成，初选 LLM 缺少新闻与情绪。
- 负面催化剂 veto 依赖 `news_data`，若新闻晚到，本轮不会生效。

建议：

1. 研判触发时生成 `research_cycle_id`。
2. 等待 market/sentiment/news 三类数据，或设置最大等待时间，例如 20 秒。
3. 超时后明确标记缺失维度，而不是静默降级。

### P1-2：异步 Agent 中仍有同步 ccxt 调用，会阻塞事件循环

严重级别：`Medium-High`  
影响范围：行情采集、风控响应、Telegram、消息延迟  
证据：

- `MultiDataCollector._full_collect()` 中 `self.exchange.fetch_ohlcv()` 是同步调用。
- `_fetch_price_tick()` 中 `self.exchange.fetch_ticker()` 是同步调用。
- `_collect_4h()` / `_collect_1d()` 中也是同步调用。
- `MultiExecutor._handle_risk_alert()` 内部分支直接调用 `close_position()` / `reduce_position()`，不是全部 `asyncio.to_thread()`。

风险：

- 网络慢、交易所 API 卡顿时，会阻塞整个事件循环上的同 Agent 工作。
- 高频采集多个标的时，price tick、risk alert 和 system command 的处理延迟增加。

建议：

1. 所有同步 ccxt 调用统一封装为 `await asyncio.to_thread(...)`。
2. 为交易所调用增加统一 timeout/retry/rate-limit wrapper。
3. 将 public REST 的 `aiohttp.ClientSession` 复用，避免每次请求新建 session。

## 5. 架构与 Flow 审计

### 5.1 启动 Flow

```text
run_agents.py
  -> 创建 Orchestrator
  -> load_config()
  -> register research/trading agents
  -> asyncio.run(_run)
  -> 启动所有 agent.run()
  -> 5 秒后首次 research_trigger
```

优点：

- 主入口清晰。
- 支持 Telegram `/restart` 通过 `data/.restart_flag` 触发重启。
- `Orchestrator` 有 SIGINT/SIGTERM graceful shutdown。

问题：

- `run_agents.py` 外层手动创建 event loop，但 `Orchestrator.start()` 内部又 `asyncio.run()`，外层 loop 实际没有承载任务，结构略混乱。
- 当前配置加载会读取真实 `config.yaml`，但测试默认切换到临时目录，容易导致生产配置未被测试覆盖。

### 5.2 研判层 Flow

```text
research_trigger
  -> MarketScanner: OKX tickers + funding + OI + SL structure
  -> SentimentResearcher: fear/greed + CoinGecko + Binance taker
  -> NewsResearcher: RSS headlines
  -> ResearchSynthesizer: preliminary symbols
  -> Censor: devil's advocate
  -> ResearchSynthesizer: final symbols
  -> SymbolRouter: active symbol update
```

优点：

- 初选 + 言官 + 终选的结构有助于降低 LLM 单点偏见。
- MarketScanner 已过滤非 crypto 合约和上线不足 1 年标的。
- 负面新闻 veto 设计方向正确。

问题：

- Synthesizer 不等待 sentiment/news，存在竞态。
- LLM 终选如果过度收窄有保底，但保底逻辑仍依赖 preliminary 数据质量。
- `SymbolRouter` 的 active symbols 不持久化，重启后依赖首次研判恢复。

### 5.3 交易层 Flow

```text
symbol_update
  -> MultiDataCollector
  -> market_data:symbol
  -> MultiTechAnalyst
  -> tech_analysis:symbol
  -> MultiJudge
  -> trade_decision:symbol
  -> MultiExecutor + PaperExecutor
  -> execution_result:symbol
  -> Reviewer + RiskGuard + PositionAnalyst + Telegram
```

优点：

- `market_data` 带 `data_quality`，低于 6/9 维度时 Judge 强制 hold。
- TechAnalyst 使用已闭合 K 线 `iloc[-2]`，降低前视偏差。
- Judge 将 LLM 降为修正因子，不让 LLM 绕过规则、EV、R:R、RSI 和风控。
- PaperExecutor 与实盘 Executor 并行，便于影子验证。

问题：

- 高频 price_tick 和低频 market_data 在同一 MessageBus 内，虽然有优先级和背压，但 Agent 自身 sleep 会带来延迟。
- 部分数据采集串行处理所有 active symbols，标的多时延迟会放大。
- 外部 API 缺失时可能导致过度 hold，需要区分“不可交易”与“辅助数据缺失”。

### 5.4 持仓管理 Flow

```text
PositionAnalyst 每 1h
  -> 7 因子评分
  -> position_review:symbol
  -> BehavioralCritic
  -> position_verdict:symbol
  -> PositionAnalyst 仲裁
  -> trade_decision:symbol
  -> Executor 执行加仓/减仓/平仓
```

优点：

- 硬性规则覆盖批判官/分析官意见，避免 LLM 拖延止损。
- 高时间框架顺向时保护持仓，减少“刚洗盘就平仓”。
- 加仓/减仓路径已经和 Executor/RiskGuard/Telegram 同步字段打通。

问题：

- PositionAnalyst 只在本地内存中缓存 tech/price；重启后需等待新数据才能评估。
- 批判官 LLM 失败时有规则降级，合理；但 schema 未强约束。

## 6. Agent 与消息总线审计

### 6.1 MessageBus

优点：

- 支持 `topic:symbol`、`topic:*`、broadcast。
- 使用 `PriorityQueue`，risk/halt/trade decision 优先级高于 market_data。
- 背压机制会丢弃低优先级消息，避免高频数据压垮队列。
- 有 dead letter 和 metrics。

风险：

- 进程内 at-most-once 消息，进程崩溃会丢消息。
- 没有 ack/retry；critical 消息如果 Agent 处理异常，只靠 Agent run loop catch 后继续。
- Agent 正在 `tick()` sleep 时无法立即取高优先级消息。

建议：

- 保持 in-memory bus 作为 MVP 可以接受，但 critical flow 应加延迟监控。
- `/status` 应展示每个 agent pending、dropped、dlq。
- 后续如果实盘扩大资金，可考虑轻量持久化 critical event journal。

### 6.2 Agent 生命周期

优点：

- BaseAgent 统一 setup/on_message/tick/publish。
- LLM lazy init，未配置时自动规则降级。

风险：

- `tick()` 被用作周期调度并包含 sleep，是当前最大调度隐患。
- 个别 Agent 选择手动 drain queue，说明 BaseAgent 模型已经不完全适合高频系统。

建议：

重构目标：

```text
agent.run()
  -> message_loop task: 永远快速 receive/on_message
  -> periodic_loop task: 独立按 next_run_at 执行周期任务
```

## 7. LLM 审计

### 7.1 当前 LLM 使用点

| 模块 | LLM 作用 | 是否可降级 |
|---|---|---|
| `ResearchSynthesizer` | 初选/终选标的 | 是，规则 fallback |
| `Censor` | 逆向审查 | 是，规则 fallback |
| `MultiTechAnalyst` | 技术解读摘要 | 是，规则 fallback |
| `MultiJudge` | 决策修正因子 | 是，规则 fallback |
| `BehavioralCritic` | 行为偏差检测 | 是，规则 fallback |

### 7.2 正向设计

- `LLMClient` 有 timeout、max_retries、rate limit。
- `chat_json()` 会加安全前缀，提示用户消息不可覆盖系统规则。
- 有 prompt injection pattern 检测。
- Judge 使用 schema 限定 action/confidence。
- LLM 不直接下单，Executor 仍做风控、余额、预检。

### 7.3 风险点

- schema 覆盖不完整。
- LLM audit log 可能泄露策略上下文。
- LLM 可用性只在调用时失败降级，缺少全局 degraded 指标和告警。
- 默认模型名、base_url 是否可用依赖环境配置，启动时只做初始化，不做健康探测。

建议：

1. 为所有 LLM JSON 输出补 schema。
2. 增加 LLM 健康状态进入 Telegram `/status`。
3. 审计日志支持关闭、脱敏和按天清理。

## 8. 执行与风控审计

### 8.1 正向设计

Executor 具备以下关键能力：

- 合约 `contractSize` 处理。
- `OrderCapabilities.precheck_order()` 做 amount/cost/precision 预检。
- `IdempotencyGuard` 防 10 秒内同向重复开仓。
- OKX `clOrdId`。
- `LiveLedger` 通过 `fetch_order` 记录真实成交价与 PnL。
- `sync_positions()` 以交易所真实持仓为准。
- 本地止损兜底、移动止损、分批止盈。
- Daily Hard Stop 触发后全平。

Judge 风控能力：

- R:R 门。
- EV 门。
- RSI 极端值保护。
- 4h RSI 二级保护。
- 风险预算：保证金、最大亏损、杠杆由 SL 距离推导。
- 弱信号杠杆上限。
- 并发持仓上限。
- 原型 cooldown。

RiskGuard 能力：

- 单仓浮亏。
- 组合回撤。
- 闪崩。
- 高杠杆。
- 相关性风险。
- 持仓超时。
- trailing stop。

Reviewer 能力：

- 交易历史。
- rolling win rate / profit factor。
- Daily Hard Stop。
- 连续亏损熔断。

### 8.2 主要风险

1. Judge 重启态不恢复会绕过并发上限和冷却。
2. 对账路径可能因为 symbol/凭证问题无法可靠恢复。
3. OKX TP/SL 行为需要 testnet 证据。
4. `RiskManager` class 默认与当前实际配置同为 500/300；直接实例化时仍应确认调用方是否期望读取统一配置。

优点：

## 14. 总体判断

该项目已经具备一个真实交易系统的主要骨架：数据采集、研究、决策、执行、风控、复盘、远控和测试都已存在，不是简单 demo。但它目前最需要解决的是“实盘一致性”和“运行态可靠性”，不是再堆更多策略因子。

当前适合：

- 继续离线回测。
- 继续 PaperExecutor 影子交易。
- OKX testnet 矩阵验收。
- 极小额、强监控、明确硬限制的灰度。

当前不适合：

- 直接按默认配置实盘运行。
- 在未修复对账/重启状态前扩大并发标的或资金。
- 依赖 Telegram `/resume` 作为唯一恢复手段。

最重要的改进顺序是：先把风控配置和状态恢复做成不可错，再处理 Agent 调度延迟，然后补真实交易所验收矩阵。
