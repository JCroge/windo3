## 4. 当前问题清单

### P1-1：Synthesizer 第 2 轮及以后可能丢弃新周期 sentiment/news，导致研判上下文缺失

证据：

- `agents/orchestrator.py:127-150` 每次 `research_trigger` 都带新 `cycle_id`
- `agents/research/sentiment_researcher.py:50-55`、`agents/research/news_researcher.py:66-72` 会带当前 `cycle_id` 发布
- `agents/research/synthesizer.py:117-127` 只有 `research_market_data` 能开启新 cycle；非 market 数据若 `incoming_cycle != _current_cycle_id` 会被直接丢弃
- `agents/research/market_scanner.py:44-129` 市场扫描包含全市场 ticker、上线时间过滤和 enrich，通常比 sentiment/news 更慢

影响：

首轮 `_current_cycle_id=None` 时问题不明显；第二轮及以后，如果 sentiment/news 先返回，Synthesizer 会把它们当作旧周期不匹配数据丢掉。market 后到时只能用 market 数据或等待超时降级，研判会失去新闻和情绪上下文，负面新闻 veto、社交热度、恐贪等信号可能缺席。

建议：

改为按 `cycle_id` 分桶缓存三路数据，例如 `_pending_by_cycle[cycle_id][msg_type]`；任一路新 `cycle_id` 都可初始化桶，但只对当前/最新 trigger 对应桶触发 synthesis。保留过期 challenge 过滤逻辑。

验收：

- 新增测试：第二轮 sentiment/news 先到、market 后到，最终 `research_preliminary` 包含同一 `cycle_id` 的三路数据
- 新增测试：旧 cycle late market/challenge 被丢弃，不污染当前 cycle

### P2-1：Executor 多个拒单路径不发布 `execution_result`，会让 Judge pending 槽位悬挂

证据：

- `agents/trading/judge.py:1164-1166` Ranking selected 后先加入 `_pending_open_symbols`
- `agents/trading/judge.py:298` 只有收到 `execution_result` 才释放 pending
- `agents/trading/executor.py:81-85` 熔断或 reconciliation pending 时拒绝开仓但直接 `return`
- `agents/trading/executor.py:126-129` 开仓失败 cooldown 中直接 `return`
- `agents/trading/executor.py:188-190` 已有持仓时非 PA 开仓信号直接 `return`

影响：

这是保守型风险，不会导致超仓，但可能导致可用槽位被永久占住，直到进程重启或人工干预。尤其是在 Ranking 选中后、Executor 执行前发生 halt/resume 的情况下，恢复后 pending 仍可能阻塞后续开仓。

建议：

Executor 对所有 open_long/open_short 拒绝路径统一发布：

```python
{"status": "rejected", "reason": "...", "action": action, "symbol": symbol}
```

同时 Judge pending 增加 TTL 兜底，例如 120 秒未收到执行结果自动释放并记录 warning。

验收：

- halt/reconciliation/cooldown/existing-position 四类拒单均触发 `execution_result:rejected`
- Judge 收到 rejected 后 pending 释放
- selected 后 Executor 无响应时 TTL 自动释放 pending

### P2-2：`rank_flush_delay` 缺环境变量映射，运维无法按启动配置调整

证据：

- `utils/config_loader.py:38` 已有 `rank_flush_delay` 硬限制
- `utils/config_loader.py:76` 已有默认值 `5.0`
- `utils/config_loader.py:260` banner 会打印 flush 窗口
- 但 `utils/config_loader.py:129-159` 的 `env_map` 没有 `RANK_FLUSH_DELAY`

影响：

启动 banner 看起来像可配置项，但 `.env` 无法覆盖；在不同市场波动和数据批次延迟下，Ranking 窗口不能通过运维配置调整。

建议：

在 `env_map` 增加：

```python
"RANK_FLUSH_DELAY": ("rank_flush_delay", float)
```

并在 `.env.example`、`docs/runbook.md` 补充该变量。新增越界测试，验证 `<1` 或 `>30` 拒绝启动。

### P2-3：PnL Reconciler 已有模块和单测，但未接入运行期定时告警

证据：

- `utils/reconciliation.py:21-130` 实现账单 PnL 对账
- `test_reconciliation.py` 覆盖空账单、偏差、本地缺失、API 失败
- `rg` 结果显示生产代码没有实例化 `utils.reconciliation.Reconciler`；当前 Telegram `/reconcile` 使用的是 `utils.position_reconciler.PositionReconciler`

影响：

代码具备“账单 PnL vs 本地 ledger”对账能力，但运行系统不会周期执行，也不会把偏差推送 Telegram。外部 SL/TP、手续费、部分成交或 ledger 漏记造成的 PnL 偏差，只能靠人工测试发现。

建议：

在 `MultiExecutor.tick()` 或独立 `ReconciliationAgent` 中每 10 分钟执行 `Reconciler.run_and_report()`；返回告警时发布 `risk_alert` 或直接 Telegram 文本。注意 API 查询失败要当成 warning，而不是静默。

### P2-4：BaseAgent 消息循环和 tick 并发后，部分 Agent 状态修改缺锁

证据：

- `agents/base.py:55-59` 现在将 `_message_loop()` 与 `_periodic_loop()` 并发运行
- 多个 Agent 的 `tick()` 会遍历/修改内部状态，例如 `agents/trading/portfolio_risk_guard.py:176-188` 遍历 `_positions`、`_price_history`
- 同时 `on_message()` 可处理 `execution_result`、`price_tick`、`system_command` 修改这些状态

影响：

这次并发拆分解决了 tick sleep 阻塞消息消费的问题，是正确方向；但状态容器缺少锁或 snapshot 约束，长时间运行下可能出现状态读写竞争、偶发漏判或持久化中间态。当前已有 `list(self._positions.keys())` 之类局部防护，但不是系统性约束。

建议：

对共享状态较多的 Agent 增加 `asyncio.Lock`，或建立模式约束：on_message 只写入队列/snapshot，tick 统一消费。至少先覆盖 PortfolioRiskGuard、PaperExecutor、MultiDataCollector。

### P3-1：`max_concurrent_positions` 仍是代码默认值，未进入统一配置/文档口径

证据：

- `agents/trading/judge.py:85-88` 默认最多 3 个并发持仓
- `utils/config_loader.py` 只有 `max_active_symbols`，没有 `max_concurrent_positions`
- `.env.example`、`docs/runbook.md` 未列该变量

影响：

当前并发持仓上限实际生效为 3，但运维文档只有“最大活跃标的 5”，容易误以为最多持仓数也是 5。它不会直接导致超仓，反而可能让开仓率低于预期。

建议：

把 `MAX_CONCURRENT_POSITIONS` 纳入 `load_config()`、硬限制、`.env.example` 和 runbook；明确区分“活跃监控标的数”和“实盘并发持仓数”。

## 5. 实盘效果推断

基于当前工程和前序真实回测结果，不能给出可靠“胜率/日化”承诺。系统现在的主要变化是降低错误开仓和超发，不是证明策略 edge 已经成立。

保守推断：

- 开仓率：会明显低于早期版本。研判层筛选、Judge 分数门、EV 门、15m 过滤、Ranking Top-N、并发 3 仓共同收紧，实际可能表现为每天 0-3 笔，行情强趋势时更高，震荡或信号冲突时可能长时间 0 笔。
- 胜率：工程过滤后理论上应高于无 15m/无 EV/无 Ranking 的版本，但现有真实回测曾显示 PF=0.33，不能据 mock 单测推断正收益。未完成连续 paper/testnet 前，胜率应按未知处理。
- 日化：当前没有足够证据支持稳定正日化。以当前 30 USDT 单笔保证金、5x 杠杆、并发 3 仓，即使方向正确，绝对收益也会被低风险额度限制；若策略 edge 未被真实数据证明，日化可能为负。
